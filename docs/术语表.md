## 一层 Transformer 里的 4 个通信调用点（TP=8 + SP）
| 名字 | 是什么 | 通信 |
|---|---|---|
| QKV | 注意力层第一步：把输入投影成 Q、K、V 三个矩阵 | 先 AG（AllGather，各卡把自己那份拼起来）再 GEMM |
| o_proj | 注意力层最后一步：把注意力输出投影回 hidden 维 | 先 GEMM 再 RS（ReduceScatter，求和后每卡拿一份） |
| fc1 | MLP 第一层：hidden → ffn。SwiGLU 有 gate 和 up 两个矩阵，常合成一个 GEMM（gate_up） | 先 AG 再 GEMM |
| fc2 | MLP 第二层：ffn → hidden（也叫 down） | 先 GEMM 再 RS |
| up / gate_up | fc1 的两种宽度：只算 up（宽 ffn/8），或 gate 与 up 合算（宽 2·ffn/8） | — |
| down | 就是 fc2 | — |

## 对比的几种做法
| 名字 | 是什么 |
|---|---|
| 原版 | 厂商 GEMM（hipBLAS）+ RCCL 集合通信，串行执行 |
| 重叠方法（创新点 1） | 分块直推融合算子：GEMM 切 8 块，算完一块就用拷贝引擎推给对端，通信藏在后面几块 GEMM 后面 |
| DX | 重叠方法的内部代号（Direct eXchange，直接交换），论文里不出现 |
| 拆批 | 把 batch 拆 2 或 4 份，一份的 RCCL 通信和下一份的 GEMM 在两条流上同时跑 |
| 预测器（创新点 2） | 训练开始前，按形状预测每个调用点用哪种做法（重叠方法 / 拆批 / 原版），选定后整个训练不变 |
| 空对照 | 环境和重叠方法完全一样，但一个算子都不接管；用来分离"重叠本身的收益" |

## E2E 实验的配置名

| 名字 | 四处调用点各用什么 |
|---|---|
| base（原版） | 四处都用厂商 GEMM + RCCL 串行 |
| fnull（空对照） | 环境、对称堆、包装层都和重叠方法一样，但一个算子都不接管，用来扣掉环境本身的影响 |
| fdk（只换纯 RS） | 只把反向里旁边没有 GEMM 的独立 RS 换掉 |
| fbag（RS 两处用重叠方法） | o_proj、fc2 用重叠方法，反向的 AG+dgrad（反向里的 AllGather 加求输入梯度的 GEMM）也融合；QKV、fc1 用原版 |
| fbc（四处全用重叠方法） | fbag 再加 QKV、fc1 |
| fcq（fbag + 只 QKV） | fbag 基础上只有 QKV 也用重叠方法 |
| fcl（fbag + 只 fc1） | fbag 基础上只有 fc1 也用重叠方法 |
| fcth / fchs（测 host 时间的两个臂） | 四处全开，同时记录 host 发命令时间：fcth（融合版）记融合 AG，fchs（原版对照）记同一批调用点用原版时的时间 |
| fat（旧在线分派器） | 训练开头逐项试开关，在本平台有偏差（F44），已不用 |

### 为什么要分这么多配置，而不是"全串行 / 全重叠 / 全拆批"三选一
预测器（创新点 2）的目标就是**每个调用点各自选最快的做法**，因为没有一种做法在所有调用点、所有模型上都最快：
- 全用原版（base）：放弃了 RS 两处的收益（算子级 GEMM+RS 在 M≥16384 21/21 格赢，几何均值 1.34–1.50×）。
- 全用重叠方法（fbc）：AG 两处在小 M 上输（算子级 GEMM+AG 在 M8192 只赢 6/22 格），而且融合 AG 每次调用的 host 发命令时间是 3.4–4.9 ms，原版只要 0.35 ms。结果是 27B 上 fbc 比 fbag 慢 2.4–3.1%，70B 上反而快 0.6–2.8%。
- 全拆批：拆批只在中等 M 有用，大 M 不如重叠方法，小 M 没有收益。
所以最优解是混合的，而且随模型变：27B 最优是 fbag（RS 用重叠、AG 用原版），70B 最优是 fbc（四处全用重叠）。

fcq、fcl、fcth、fchs 这几个**只是给预测器做拟合和检验用的测量臂**：它们把"QKV 单独开"和"fc1 单独开"的贡献、以及 host 发命令时间分开测，用来检验预测器能否预先算对每个调用点的增减。论文 E2E 主表只放 base（原版）、fnull（空对照）、fbc（全用重叠方法），以及预测器选出的配置。

注意：拆批目前只在算子级测过，还没接进训练（E2 待办），所以现在 E2E 配置里只有"重叠方法 / 原版"两种选择。

## 计时与指标
| 名字 | 是什么 |
|---|---|
| 单次计时 | 每测一个 op 先等 GPU 空闲，再计这一个 op |
| 连发计时（b2b） | 连续发 16 个 op 不等待，总时间 ÷ 16；更接近训练里的情况。算子级表用这个 |
| M | 一次 GEMM 处理的 token 数 = 序列长度 4096 × MBS |
| MBS | micro-batch size，每张卡一次前向处理几条样本 |
| 卡时 | 卡数 × 小时。8 卡跑 1 小时 = 8 卡时 |
| host | CPU 那一侧，负责给 GPU 发命令 |
| 控制面 | host 发命令、排队、等确认这些开销（区别于数据真正在线上传输的"数据面"） |
| fork | 开发期原版代码目录的复制品 `tri-dist-hygon-opus`；本仓库 `src/stowaway/` 即由它整理而来 |

## 预测器（11-01 定稿）用到的量
| 名字 | 是什么 |
|---|---|
| 层周期 | 一个 micro-batch 走完一层的前向 + 重算 + 反向 |
| D（每层周期 GPU 时间） | 整步时间 ÷（层数 × micro-batch 数）；由原版短跑 ≤3 次迭代得到 |
| e（GPU 空等） | 每次融合 AG 调用让 GPU 等 host 重新发命令的时间；e = 0.0096 × D（D < 205 ms），否则 0 |
| 截止点 | AG：D ≥ 205 ms（137–273 之间）时空等被盖住；RS 组：D < 111 ms（80–143 之间）时回退原版 |
| 样本内 / 留一检验 | 样本内 = 拟合用过的点再检查一遍；留一 = 每次拿掉一个点拟合，再预测这个点 |
| planner.py | 统一规划脚本：输入形状 + MBS，输出 4 个调用点各用哪种方法 |
