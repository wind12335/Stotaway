## 0. 一句话论点（升级版）

> **在厂商 GEMM 不可修改、host 控制面昂贵的加速器上，通信重叠的整步收益由控制面决定，而不是由数据面带宽决定。** 因此，重叠系统应当"控制面优先"：在 GEMM 外部切分以继承厂商库性能，用控制面开销最小的协议承载数据，并以整个训练步为单位、显式建模控制面代价来选择每个调用点的执行方式。

MoE 的结果让这个论点从"一个现象"变成"跨两类模型成立的规律"，而且有一组干净的对照：

| 模型类型 | 只优化数据面（控制面不动） | 同时消除控制面开销 | 证据 |
|---|---|---|---|
| 稠密 TP+SP | 融合 AG 孤立测试 1.29×，进训练整步反而慢 3%（host 被跨进程拷贝拉回 GPU 进度） | 预测器把控制面代价算进去，只在盖得住的形状上开 AG 融合：8 卡、16 卡选择全对 | F17、F49–F52 |
| MoE EP8 | 只换 all-to-all 数据面、保留 split 同步：整步**慢 13–18%** | 整层免 host 同步：整步**快 10.3%（1.115×）** | F24、F55 |

两行都是"同样的数据面，控制面处理方式不同，整步收益从负变正"。这是全文最有说服力的证据链，摘要和 Introduction 都应该围绕它写。

## 1. 摘要骨架（v3）

1. **背景**：万亿参数模型（稠密与 MoE）的分布式训练中，张量并行的 RS/AG 和专家并行的 all-to-all 占比越来越高，计算通信重叠是主要优化方向。
2. **问题**：现有细粒度重叠方法大多在 NVIDIA 上设计，依赖可修改的 GEMM 或主机侧调度；迁移到 AMD、海光等平台后收益消失甚至为负（flux / FlashOverlap / Syncopate / Triton-distributed 在海光 DCU 上 0.3–0.9×）。
3. **原因**：① 可修改 GEMM 与厂商库的差距随平台变化（DCU 上 Triton GEMM 只有厂商库的 30–50%）；② host 控制面被忽视——稠密场景里跨进程拷贝会把 host 拉回 GPU 进度，MoE 场景里每层都要把 token 数同步回 host。
4. **系统**：XXX 在不改厂商 GEMM、不改训练框架源码的前提下，把重叠执行统一为一个设计空间（切分轴 × 切分数 × 数据面 × 控制面位置），用无栅栏协议承载数据面，用整步规划器按形状选点。
5. **效果**（摘要只报峰值和端到端）：
   - 算子级：GEMM+RS 最高 **1.84×**（DeepSeek-V3 dense 形状，M32768，连发计时），GEMM+AG 最高 1.43×；MoE 整层（前向 + 反向）最高 1.57×。
   - 端到端：稠密 27B / 70B 训练 1.05–1.08×（对空对照），双机 16 卡同样成立；MoE 训练 1.115×。
   - 规划器：在 8 卡和双机 16 卡上为两种模型选出了相反的最优配置，且都选对。

## 2. 设计空间（v3：加"控制面位置"一维）

| 维度 | 取值 | 说明 |
|---|---|---|
| 切分轴 | 不切 / 输出行（依赖序）/ batch（独立批）/ 专家（虚拟分组） | 专家维的"虚拟分组"= 每个专家在设备上切成 ≤B 行的块，固定网格覆盖任意路由 |
| 切分数 | 1 / R / 2–4 / ⌈T/B⌉ | — |
| 数据面 | 拷贝引擎 / 集合通信库内核 / SM 直写 | 三角规律：引擎不占 CU 但要 host 定尺寸；SM 不要 host 但抢 CU；RCCL 居中（F22b） |
| **控制面位置** | host 定尺寸（需同步）/ 设备常驻（尺寸只在 GPU 上） | **新维度**。稠密 RS/AG 尺寸静态，host 定尺寸代价只在入队；MoE 尺寸动态，必须设备常驻 |

各方法在空间里的位置（Related Work 的核心表）：

| 方法 | 切分轴 | 数据面 | 控制面位置 | 改 GEMM | 训练端到端 | 与我们的关系 |
|---|---|---|---|---|---|---|
| flux / FlashOverlap / Syncopate / Triton-dist | 输出 tile | SM | 设备 | 要 | 有（NVIDIA） | DCU 上 0.3–0.9×，被支配 |
| PyTorch Async-TP | 输出行 | 拷贝引擎 | host，每步全局屏障 | 不要 | 有（NVIDIA） | 同轴同面；我们无屏障（票据 + 流等待） |
| FiCCO（AMD，2025-12） | 输出行 | DMA | host | 不要 | 无（算子级） | 只做 AG 类、明确不做 RS；启发式不含控制面 |
| ISO / TokenWeave / Domino | batch | 集合通信库 | host | 不要 | 有 | 我们的"拆批"档，按形状纳入候选 |
| DeepEP 低延迟 / MORI-EP / HybridEP | 专家 | SM / RDMA | 设备 | — | DeepEP、HybridEP 有 | 我们的 MoE 数据面属同类；我们把它和免同步分组 GEMM、整步规划放进同一框架，并在 DCU 上给出控制面对照实验 |
| Primus-Turbo 分组 GEMM / hipBLASLt 示例 | 专家 | — | 设备 | 用 CK / 厂商库 | — | 我们的虚拟分组用闭源 hipBLASLt 实现，绕开组数在 host 固定的限制 |

**我们的点**：输出行 × 拷贝引擎 × 无屏障票据（稠密 RS/AG），batch × RCCL（中 M），专家 × SM × 设备常驻（MoE），原版（兜底）。贡献是：测出这个空间在 DCU 上的支配关系（含大量负结果），并用规划器按形状自动选点。

## 3. 贡献列表（v3，每条都配了"与先例的差别"）

1. **刻画（新意最强）**：首次在 DCU 真实训练整步上量化重叠收益缩水的原因，提出四类损失分类，发现两条控制面定律：
   - (a) 跨进程拷贝会把 host 同步到 GPU 进度附近，与拷贝次数、大小、API 无关（F50）；
   - (b) MoE 中只优化数据面会让整步变慢，消除控制面才变快（F24 vs F55）。
   - 另含置换定律和 DTK 图捕获限制。先例都没有整步层面的控制面刻画。
2. **设计空间与协议**：把稠密与 MoE 的重叠执行统一为（切分轴 × 切分数 × 数据面 × 控制面位置）设计空间。为拷贝引擎数据面设计**无栅栏置换票据协议**：无 incast、O(R) 控制面开销、偏斜曝露 max(0, δ−W)，并扩展到反向（AG 到达即算 dgrad）。
   - 与 Async-TP 的差别：无全局屏障。
   - 与 FiCCO 的差别：覆盖 RS 和反向，并在训练端到端兑现。
3. **整步规划器（新意次强）**：代价模型分两级。第一级是算子级时间模型加安全门，第二级是控制面项（每次融合调用造成的 GPU 空等，随每层 GPU 时间变化，有截止点）。另外证明在线探测在本平台上原理上有偏：建立通信上下文会持久改变后续算子性能（F44），因此采用离线预测。
   - 与 FiCCO 启发式、Centauri、Oases 的差别：它们只建模算子本身，不含控制面，也不讨论探测偏差。
4. **实现与评测**：在 Megatron 上实现，不改厂商 GEMM、不改 Megatron 源码。覆盖 11 个模型形状的算子矩阵（GEMM+RS 33 格、GEMM+AG 66 格）、27B/70B 稠密训练（8 卡 + 双机 16 卡）、Qwen3-30B-A3B 形状 MoE 训练（EP8）。MoE 侧的免同步 dispatch/combine 和分组 GEMM 写成"框架在 MoE 上的实例"，正文明确引用 DeepEP、MORI-EP、Primus-Turbo。

## 5. 审稿风险与应对（v3）

1. **FiCCO 被当成直接先例**（风险最大）：同为 AMD 平台、DMA、不改 hipBLASLt、带启发式。**不单开"与 FiCCO 对比"一节**（显得心虚），按三处自然出现（11-02 用户定）：
   - **Introduction / Related Work**：正面引用 FiCCO 和 PyTorch Async-TP，说明它们没有发现、没有解决的问题：只做 AG 类、不做 RS 和反向；每步屏障或主机侧调度；只在算子级评测，没发现控制面会吃掉整步收益；启发式只建模算子，不含控制面。
   - **System Design**：只讲我们的架构，在设计决策处用一句话点出取舍。例如"无全局屏障：票据随数据走、等待只放流上（对比基于屏障的设计 [Async-TP]）"，不展开对比。
   - **Evaluation**：把 FiCCO 式做法当作普通基线和消融放进实验，用数据说话：
     ① 算子级表加一列"FiCCO 式调度"（在我们的框架内按其论文复现：DMA、同时向所有对端扇出、主机侧调度）；
     ② 协议消融：我们的无屏障票据 vs 每步屏障（Async-TP / FiCCO 式）vs 扇出（incast）；
     ③ 规划器准确率：FiCCO 式静态启发式（按 GEMM 维度）vs 我们的两级模型，同一批调用点、同一套实测标签。
   - **FiCCO 原文要点（11-02 精读 docs/Design Space Exploration of DMA based.pdf，arXiv 2512.10236）**：
     - 平台：MI300X **全互联拓扑**，每链路 64 GB/s。
     - 核心论点：逐对端（shard-level、P2P，Async-TP 式）在全互联上链路闲置，通信慢 7×；所以把通信再切细 1/8，所有对端同时发（all-to-all 扇出）。
     - 数据面：hipMemcpyDtoDAsync，多流，对称内存。
     - 范围：AG 类和 EP all-to-all；**明确不做 RS**（"DMA engines do not support math"）。
     - 4 种调度（uniform/hetero × fused/unfused × 1D/2D，其中 2D 是模拟的）。
     - 启发式：静态 OTB × MT 对比机器阈值，研究场景全对，16 个合成场景对 81%，错选损失约 14%。
     - 评测：只有算子级 16 个 GEMM 场景，最高 1.6×，达到理想值的 46–52%。
     - **对 CPU 发射开销的态度**："只在算子特别小时有影响，图捕获可以控制"。
   - **由此得到三条不卑不亢的定位**（写进 Related Work / Design 的一句话里）：
     ① **拓扑决定调度方向**：FiCCO 在全互联上证明扇出优于逐对端；DCU 是交换式拓扑，我们实测逐对端置换序满速（约 141 GB/s/rank），而扇出 = 每个接收端同时被所有对端写入（incast），孤立测慢 10–19%，流水中慢 30–70%。两者并不矛盾，正好说明调度方向要由平台定律决定，这就是设计空间加规划器的价值。FiCCO 式扇出作为空间里的一个点，在 Evaluation 里实测。
     ② **控制面不是"小算子才有的发射开销"**：FiCCO 认为图捕获可以消掉它；我们在训练整步里实测，它是收益缩水的主因（融合 AG 孤立 1.29×、整步 −3%）。DTK 上图捕获会把多流 DAG 串行化、双图会互等死锁（F37），而且跨进程拷贝会把 host 拉回 GPU 进度（F50），与发射次数无关。
     ③ **RS 与反向**：FiCCO 认为 DMA 不能做 RS；我们用"DMA 推送 + 接收端一次融合求和"做了 GEMM+RS（含反向 AG+dgrad），这是稠密训练里收益最大的部分（算子级最高 1.84×）。
2. **MoE 部分被认为是拼盘**：
   - 应对：MoE 不单列贡献，只作为论点 1(b) 的证据和框架普适性的展示。
   - 1.115× 放在 Evaluation，同时给出"只换数据面 0.85–0.88×"的对照，这一对比本身就是贡献。
3. **端到端幅度 5–11%**：用"从负到正、永不变慢"的叙事接住。
   - 现有系统 0.3–0.9× 对我们 1.05–1.08×；MoE 只换数据面 0.85×，消除控制面后 1.115×。
4. **单平台**：A800 移植之前，讨论节写适用条件（厂商 GEMM 不可改、控制面昂贵），并推断 NVIDIA 上的表现。

## A. 摘要骨架（五句话）

1. **背景**：大模型参数量已达万亿级（如 Kimi K2 约 1T、DeepSeek-V3 671B），张量并行中的集合通信占比随之上升，计算通信重叠是其中最主要的优化方向之一。
2. **问题**：现有细粒度重叠方法大多针对单一平台（主要是 NVIDIA）设计，并在 GEMM 内部插入通信，依赖可修改的 GEMM 实现（CUTLASS、Triton）。将同样的原理迁移到 AMD、海光等平台后，优化收益消失甚至变为负值（我们实测 flux / FlashOverlap / Syncopate / Triton-distributed 在海光 DCU 上只有原版的 0.3–0.9×）。
3. **原因**（正文重点论证，两条均有实测）：
   - 可修改 GEMM 与厂商调优计算库（cuBLAS、hipBLAS/hipBLASLt）的性能差距随平台变化：NVIDIA 上 CUTLASS 与 cuBLAS 接近，海光 DCU 上没有 CUTLASS，Triton GEMM 只有厂商库的 30–50%（106–172 TF 对约 361 TF）。在 GEMM 内部融合的方法因此无法继承厂商库的性能。
   - host 控制面开销被忽视：在 GEMM 外部切分会带来 host 入队、引擎队列反压和跨 rank 确认链等开销（一次融合调用 host 5.4–5.7 ms，同样的推送在空闲设备上只要 0.056 ms），算子级收益进入训练整步后大幅缩水（孤立测 1.29× 的融合算子，整步反而慢 3%）。
   - **措辞**：不写"已有研究未能利用厂商 GEMM 库"。写"细粒度融合类方法依赖可修改的 GEMM 实现；在可修改 GEMM 与厂商调优库差距较大的平台上，它们无法继承厂商库的性能"。
4. **系统**：我们提出 XXX，在不修改厂商 GEMM、不修改训练框架源码的前提下实现跨平台的计算通信重叠。XXX 由三层组成：
   - **抽象层**：把每个"GEMM + 集合通信"调用点的执行方式统一描述为（切分轴 × 切分数 × 数据面）构成的重叠设计空间；
   - **协议层**：为拷贝引擎数据面设计无栅栏置换票据协议，控制面开销与数据量无关，只为落后者付出 max(0, δ−W) 的等待；
   - **规划层**：以训练整步为目标、显式建模 host 控制面预算，为每个调用点在设计空间中选择执行方式。
5. **效果**（摘要只报峰值，均值放 Evaluation）：
   - 算子级（融合算子，GEMM+通信）：在海光 DCU 上最高 **1.81×**（GEMM+ReduceScatter，生产算子，DeepSeek-V3 dense 层形状 M32768；11 模型 33 格矩阵中 M≥16384 全部 22 格获胜，几何均值 1.44–1.68×），AG+GEMM 最高 1.355×（待补第 2 轮）；在 NVIDIA A800 上最高 **1.xx×**（待测）。生产算子 11 模型矩阵（opus_day1031/prodop.log）跑完后，若出现更高且可信的格子再更新。
   - 纯通信 RS 的 1.60× **不进摘要**：它是集合通信库之间的比较，不是计算通信重叠，且部分来自 RCCL 在本平台带宽偏低。放在协议层的数据面微基准小节，用来支撑置换定律和独立 RS 调用点（位置①）。
   - 端到端一句带过：在 Megatron 训练中获得端到端加速（具体数字见 Evaluation）；vLLM prefill 有数据后再加。

## B. 峰值数字的口径（防审稿人质疑）

| 数字 | 来源 | 可信度核查 |
|---|---|---|
| 1.60×（仅微基准，不进摘要） | 纯 RS 537 MB，dx 3.929 vs RCCL 6.287 ms | 两次独立批复现（F4 1.57×、F33 1.60×），位级 md=0；是通信库对比，不是融合算子 |

## 1. 为什么"三个算子 + 分派器"撑不起 CCF-A

审稿人读到"我们提出算子 A、算子 B、外加一个选择器"，会给出三条意见：
1. 每个算子单独看都有先例（MORI、CoCoNet、ISO、TokenWeave），是增量工作；
2. 三个算子之间没有联系，像是把能赢的格子拼在一起；
3. 选择器只是调参。

要回答这三条，论文需要三样东西：**一个统一的问题刻画**（说明这些技术为什么是同一个问题的不同解）、**一个设计空间**（说明三档是空间里有原则地选出来的点，并且其他点我们测过、它们更差）、**一个有模型的规划器**（说明选择是可预测的，而不是试出来的）。

我们手里的数据正好够撑这三样，只是之前没有这样组织。

## 2. 核心论点（thesis）

> **在可修改的 GEMM 远慢于厂商 GEMM、host 控制面昂贵的加速器上，通信×计算重叠的整步收益受 host 控制面约束，而不是受数据面带宽约束。因此重叠必须满足三点：在 GEMM 外部切分（不改 GEMM）；用控制面开销尽量小的协议承载；以整个训练步为单位做规划。**

这句话把我们一周的发现串成一条因果链：
- "可修改 GEMM 远慢于厂商 GEMM"：厂商 GEMM（DCU 上 hipBLAS/hipBLASLt，NVIDIA 上 cuBLAS）在任何平台都不可修改；关键是可修改 GEMM 与它的差距。NVIDIA 上 CUTLASS 与 cuBLAS 接近，DCU 上没有 CUTLASS，Triton 只有 106–172 TF 对厂商 361 TF（差 2–5×）。所以 flux / FlashOverlap / Syncopate / Triton-distributed 一类在 GEMM 内部做融合的方案移植后只有 0.3–0.9×。
- "控制面昂贵"：融合调用 host 5.4–5.7 ms，其中 7 次推送占 4–4.5 ms；同样的推送在空闲设备上只要 0.056 ms。
- "整步规划"：列并行孤立测 1.29×，进车整步 +3%；车内单 op 1.52×，整步只有 1.07×。

## 3. 系统名与组成

起一个系统名，让三档在论文里是一个系统的组成部分。名字只是标签，可以换。示例：**Weft**（纬线：把通信织进计算）。

Weft 由三层组成，每层对应一个贡献：

| 层 | 名称 | 内容 | 对应的现有工作 |
|---|---|---|---|
| 抽象层 | **重叠设计空间（Overlap Design Space）** | 把任一个"GEMM + 集合通信"调用点的执行方式描述成三元组：切分轴 × 切分数 k × 数据面 | 三档 = 空间里的三个点；其余点是我们测过的负结果 |
| 协议层 | **无栅栏置换票据协议（Fence-free Permutation Ticketing）** | 拷贝引擎数据面上的点对点协议：置换序推送、票据跟数据、等待方平面写、单调票值、读后 ack 才复用、落后块排最后消费 | DX 的协议部分 + paper #1 的票据引擎 |
| 规划层 | **整步重叠规划器（Step-level Overlap Planner）** | 对训练一步里的每个调用点，在设计空间里选一个点；代价模型含 host 控制面项；探针协议保留 host 领先量 | 分派器 + 代价模型（待完成） |

### 3.1 抽象层：设计空间（最关键的包装动作）

三档不是三个独立算子，而是同一个二维空间里的点：

| 切分轴 ＼ 数据面 | 拷贝引擎（不占 CU，host 逐块定尺寸） | 厂商集合通信内核（占 CU，host 一次调用） | SM 直写（host 一次，占 CU） |
|---|---|---|---|
| 不切分（k=1） | — | **原版**（小 M 兜底） | 测过：0/54 格 ≥1.05（F35） |
| 输出行，依赖序（k=R） | **分块直推**（大 M） | 需改写 GEMM：flux / FlashOverlap 类，DCU 上 0.3–0.9× | tile 级融合 Triton GEMM + 对称内存：Triton-distributed（本仓库移植源） |
| batch，独立批（k=2–4） | — | **拆批重叠**（中 M） | — |

再加一个正交维度"执行形态"：eager 多流 vs 图捕获。图捕获测过，DTK 上多流 DAG 被串行化、重叠丢失（F37），双图互等死锁（F37b）。

这样写有三个好处：
1. 三档有了统一定义，审稿人看到的是一个系统，不是三个补丁。
2. **我们的负结果变成了设计空间探索的证据**：SM 直写、图捕获、改 GEMM 都测过，并且解释了为什么在这个平台上它们被支配。这是 CCF-A 审稿人很看重的"为什么不用 X"。
3. 先例工作在空间里各占一个点：MORI = 输出行 × 拷贝引擎 × 改 GEMM，ISO/TokenWeave = batch × 集合通信库，flux = 输出行 × SM × 改 GEMM。我们的贡献是**测出这个空间在 DCU 上的支配关系，并按形状自动选点**。

**前提（必须补的工程）**：代码里三档要真的共享一个接口，例如每个调用点按 `(axis, k, plane)` 分发到同一套执行器。现在三档是三段独立代码，要做一次接口统一，CPU 工作约 1 天。否则"设计空间"只是论文里的表格，审稿人看代码或问实现细节时会露馅。

### 3.2 协议层：无栅栏置换票据协议

把 DX 的协议部分单独提出来，写成有性质的协议，而不是实现细节：
- **无 incast 性质**：按置换序推送时，每一步每个目的地只收一份。配合实测置换定律（任意对端 139–143 GB/s/rank，incast 时慢 10–19% 孤立 / 30–70% 流水）。
- **控制面开销**：每个 op 的 host 命令数为 O(R)，不随数据量增长。
- **偏斜容忍性质**：只等落后者那一块，并把它排最后消费，曝露 = max(0, δ − W)。实测 δ=2000 µs 时原版多付 1.92 ms，我们多付约 0.05 ms。
- **安全性**：五条定律（等待方平面、单调票值、读后 ack、票据随数据同流、等待只放流上）各对应一个踩过的死锁或撕裂（S16、R12、T18、F35、F37）。可以写成一张"违反哪条会怎样"的表，显得协议是被证伪逼出来的，而不是拍脑袋设计的。

### 3.3 规划层：整步重叠规划器

论点：**重叠决策必须以整步为单位**，因为 host 领先量是整步共享的预算，逐 op 的局部收益不能相加。证据：
- 逐 op 相加的朴素模型，预测 QKV+fc1 约 0%，实测 +2.4–3.05%；
- 前向融合 host 20.3 ms 远超设备 3.35 ms，朴素模型预测大输，实测 −4.06%。

规划器的组成：
1. **控制面预算模型**：整步 ≈ max(设备总时间, 关键路径 host 时间) + 同步耦合项。
2. **候选集**：设计空间里的点，按调用点选择。
3. **探针协议**：多迭代、边界同步，保留 host 领先量（单次同步迭代会抹掉稳态空泡）。

**这是目前最大的缺口**：代价模型还没做，现有分派器只是 3 个开关的贪心探测，而且有已知偏差（F39：70B 上把该开的列并行关掉了，损失约 2.7%）。规划层要成立，至少要做到：
- 代价模型在 ≥19 条车辆标签上回测，符号预测 ≥16/19；
- 选中配置与实测最优相差 ≤0.5%；
- 在全 MBS 曲线上不比原版慢。

## 4. 贡献列表（论文 §1 的写法）

1. **刻画**：在 DCU 的真实训练整步上，首次量化通信重叠收益为什么缩水。提出四类损失分类，其中 host 控制面是此前被忽视的一类；给出交换机拓扑上的置换定律，以及 DTK 图捕获的三条限制。
2. **设计空间与协议**：提出把"GEMM + 集合通信"的重叠执行统一描述为（切分轴 × 切分数 × 数据面）的设计空间，测出它在 DCU 上的支配关系；为其中的拷贝引擎数据面设计无栅栏置换票据协议，具有无 incast、O(R) 控制面开销和 max(0, δ−W) 偏斜容忍三条性质，并首次把它扩展到反向（AG 到达即算 dgrad）。
3. **规划**：提出整步重叠规划器，用含控制面项的预算模型为每个调用点选择设计空间中的执行方式，并给出保留 host 领先量的探针协议。
4. **实现与评测**：在 Megatron 上实现 Weft，不修改厂商 GEMM、不修改 Megatron 源码。11 个模型形状的算子矩阵、27B/70B 真实训练整步、双机 16 卡。

## 5. 摘要草稿（中文）

> 张量并行训练中，把集合通信与 GEMM 重叠是公认的加速手段，但现有方法（改写 GEMM 内核的融合算子、DMA 细粒度重叠、拆批重叠）几乎都在算子级评测。我们在国产加速器上发现，这些方法在真实训练整步中收益大幅缩水甚至变为负值：三个开源重叠系统移植后只有原版的 0.3–0.9×，孤立测试 1.29× 的融合算子进入训练后整步变慢 3%。我们定位出主要原因是 host 控制面：厂商 GEMM 不可修改迫使切分发生在 GEMM 外部，而每次切分都要付出 host 入队、引擎队列反压和跨 rank 确认链的代价。基于这一发现，我们设计了 Weft。Weft 把重叠执行统一描述为切分轴、切分数与数据面构成的设计空间；为拷贝引擎数据面设计了无栅栏置换票据协议，控制面开销与数据量无关，并且只为落后者付出 max(0, δ−W) 的等待；再用一个以整步为目标、显式建模 host 预算的规划器，为每个通信调用点选择执行方式。在 8 卡 DCU 上，Weft 在大规模 GEMM 上的算子级几何均值加速 1.18×，在 27B 与 70B 模型的真实训练整步（含重算）上加速 1.06–1.08×，并在所有形状上不慢于原版。

注意：最后一句"所有形状上不慢于原版"和"规划器"相关的表述，要等 E3 回测通过后才能保留。

## 8. 冲 CCF-A 的现实评估

**加分项**：
- 问题真实，而且有反直觉的结论：别人的重叠系统在这个平台上让训练变慢，我们让它变快且不会变慢；
- 因果链完整，有大量测量和定律；
- 负结果多，设计空间被充分探索；
- 真实训练整步数据，含重算，位级正确。

**风险项**：
1. **收益幅度**：整步 1.06–1.08×。包装改变不了这个数。应对：把对比放在"现有系统 0.3–0.9× → 我们 1.06–1.08×"上，强调"从负到正"和"永不变慢"，而不是绝对加速比。
2. **单平台**：只在 DCU 上做过。应对：在适用范围上写清楚"厂商 GEMM 不可改、控制面昂贵"这两个条件；最好在第二个平台上至少复现刻画部分（控制面损失是否存在）。
3. **规划器还没有模型**：这是 CCF-A 审稿人一定会深挖的部分。必须完成 E3。
4. **先例**：MORI、CoCoNet、ISO 都要正面引用并在设计空间表里定位，不能回避。

**结论**：按这个叙事，论文结构上具备投 CCF-A（如 ATC、EuroSys、PPoPP、SC）的形态。能不能中，取决于规划器的代价模型能否做扎实，以及收益幅度能否被"从负到正、永不变慢"的叙事接受。CCF-B 一档是比较稳的保底。
