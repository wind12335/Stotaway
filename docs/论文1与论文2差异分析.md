# 论文 2（Stowaway）与论文 1（AnchorOverlap）的差异分析

11-09 写，依据是两边的代码和论文 1 的正文。
- 论文 1：`Tri-dist-hybird/python/triton_dist/kernels/nvidia/`，正文 `related_work_1102/paper1_text/AnchorOverlap_EN_main.txt`。
- 论文 2：`stowaway/src/stowaway/kernels/gemm_rs_dx.py`。

## 0. 结论

1. **DX 重叠机制本身不能当作论文 2 的独立创新。** DX 的协议骨架和论文 1 的 RS v3 窗口化面板协议是同一套。骨架包括：引擎拷贝把数据推进对端的对称暂存槽，同一条流上紧跟一个票据，用单调序号区分轮次，消费者释放后槽位才复用，按 `(rank + step) % R` 的置换序发送。DX 的不同点大多是论文 1 设计空间里的一个角点（块 = M/R、不开窗口、单条带），或者是移植到 DCU 训练时被平台规律逼出来的工程改动。再加上 MORI（置换序 SDMA 直推）和 FiCCO（DMA 拷贝重叠）这两个先例，单靠 DX 撑不起论文。
2. **论文 2 可以独立成文。** 立足点不是"怎么重叠"，而是"什么时候重叠才值得开、在哪开"。这部分是论文 1 没有的，也不是论文 1 的配置差异：
   - 控制面定律：在本平台上，算子级赢不等于整步赢；
   - 两级预测器：逐个调用点决定开还是不开；
   - 训练整步（含反向）、推理、MoE 的全栈评测。
3. **写法**：引用论文 1（双盲期间按第三方匿名自引），把 DX 写成"沿用 [AnchorOverlap] 的票据交接协议，在厂商 GEMM 不改、训练整步的约束下重新实例化"。设计一节用一段话讲清楚取舍，DX 不列为贡献。

## 1. 两篇各做了什么

| | 论文 1 AnchorOverlap | 论文 2 Stowaway |
|---|---|---|
| 问题 | 集合通信–GEMM 链怎么重叠得更好：交接粒度、生产顺序、暂存复用 | 重叠在训练整步里什么时候才真的赚，每个调用点开不开 |
| 链路 | AG–GEMM、GEMM–RS、GEMM–AR 三条 | AG–GEMM、GEMM–RS（前向）、AG–dgrad（反向）、独立 RS；不做 AR |
| 场景 | 推理 prefill（代码全部 `@torch.inference_mode()`，`tp_attn.py` 320 行起） | Megatron 训练（前向 + 重算 + 反向）、vLLM prefill、MoE EP |
| GEMM | RS / AG 用 Triton 内核，内核里用原子计数发就绪信号、按 tile 等待；AR 用 cuBLAS 分块 GEMM（论文 §4.2.3） | 全部是厂商 GEMM（hipBLAS）按块调用，用流事件同步 |
| 平台 | 4×A100 NV12 全互连；4×K100_AI | 8×BW1000（单机）、16 卡（两机 RDMA） |
| 配置怎么定 | 两阶段搜索：短测筛结构 → 细化 SM 配额，前提是总在重叠 | 两级代价模型 + 控制面项，训练前离线决定开不开 |
| 结果 | 算子级最高 1.40×，prefill 1.02–1.22×，暂存降到 1/8 | 训练整步 1.06–1.08×（8 / 16 卡），vLLM 1.14–1.22×，MoE 1.116×；预测器 8 卡 5/5、16 卡 2/2 |

## 2. 重叠机制逐项对比

### 2.1 继承的部分：协议骨架基本一样

论文 1 RS v3 的发送函数是 `new_3rd_v3_windowed_panel_rs.py: _issue_windowed_panel_scatter_and_arrival`（469 行），DX 的是 `gemm_rs_dx.py: dx_gemm_rs_op`。两者对照：

| 步骤 | 论文 1 RS v3 | DX |
|---|---|---|
| 发送顺序 | `for step in range(W): dest = (local_rank + step + 1) % W` | `for j in range(1, R): d = (rank + j) % R` |
| 复用前等释放 | `_wait_eq_cuda(free_flag[dest][slot], free_ticket, scatter_stream)` | `_wait_value_gte(ack[d], op - 1, lane)` |
| 推数据 | `cudaMemcpy2DAsync(remote_buf_ptr, …, scatter_stream)`，拷贝引擎 | `memcpy_async(p_slots[d] + rank*bb, …, lane)`，拷贝引擎 |
| 发票据 | 同一条流上 `cuStreamWriteValue32(remote_arrival, ticket)` | 同一条流上 4 B 引擎拷贝写 `p_arr[d]` |
| 归属卡等到齐 | 对每个源 `_wait_eq_cuda(arrival[src][slot], ticket)` | 对每个源 `_wait_value_gte(arr[s], op)` |
| 归约 | 本地分块作种子 + 读远端求和（Triton 归约核） | 本地块 + R−1 份一次 fp32 求和（Triton 核 `k_dx_sum`） |
| 释放 | `_set_signal_cuda(free_flag_local[slot], ticket)` | `_launch_flag_xchg(p_ack[s] + 4*rank, op)` |
| 序号 | `ticket = round_base + chunk*B + band + 1`，单调；`last[x]` 记前驱 | `op` 计数单调；`op − 1` 就是前驱 |
| 每次调用的全员栅栏 | 无（只在 `reset_runtime_state` 时） | 无（只在建上下文时 `host.barrier_all()`） |

这些对应关系就是论文 1 的贡献 2 原文："Arrival and release states govern data writes, reads, and reclamation"。在 RS 上，DX 相当于论文 1 RS 取 `chunk_rows = M/R`、`active_chunk_window L = 1`、`n_bands = 1`，再把 Triton GEMM 换成厂商 GEMM。

### 2.2 真正不同的点

下表按"能不能在论文里讲成设计取舍"从强到弱排列。

| # | 维度 | 论文 1 | DX | 性质 |
|---|---|---|---|---|
| a | GEMM 和通信怎么耦合 | RS 生产者是 Triton GEMM，每个 tile 写完后 `atomic_add(counter)`，凑齐一个面板的 tile 再发 `chunk_signal`（`new_3rdgemm_reducescatterv3.py` 154–181 行）。AG 消费者是 Triton 内核，按 tile 用 `dl.wait(ready)` 等（`new_allgather_gemm_tileready.py` 134、303 行）。 | 厂商 GEMM 每块调一次 `torch.matmul`，块与块之间用 `hipEventRecord / hipStreamWaitEvent` 交接，内核里没有任何信号。 | **设计约束上的真实差别**。好处：训练里的 dgrad、wgrad 也能直接用厂商 GEMM；在 BW1000 上，论文 1 形态的移植只有 vendor+RCCL 的 0.32–0.42×，差距全部来自 Triton GEMM 生成的代码（36.4 vs 11.0 ms，S18，`tri-dist-hygon/bench/results/s18_*_29568.json`）。限制：论文 1 的 AR 路径已经是"cuBLAS 分块 GEMM + 流上交接"（§4.2.3），所以"块式厂商 GEMM"这一点不能说论文 1 完全没有，只能说论文 1 的 RS / AG 没这样做。 |
| b | 生产顺序 | 所有 rank **对齐**算同一个目的地（`pid_m_offset = 0`，注释写明是为了让每个目的地的"全员到齐"最早发生）；多条带路径再加**前沿优先**：先算所有目的地的前 F 个块。 | 每个 rank **旋转**：第 j 步算要给 (r+j) 的块，自己的块最后算。目的是每一步每条链路上只有一条流，不出现多卡同时往一张卡里挤（incast）。 | **设计取向相反**，原因是平台不同。A100 NV12 每对卡之间有独立链路，同时往一个目的地发不冲突，对齐顺序能让归约最早开始。BW1000 上实测按置换序推每卡约 141 GB/s，扇出和 incast 都慢，必须错开。这是最值得写进论文的一个取舍，但它属于"按平台选调度"，不是新协议。 |
| c | 交接粒度 | `chunk_rows` 面板，粒度可配，配置搜索会调它。 | 固定 M/R 一整块，即每个目的地一块。 | DX 是论文 1 设计空间里的一个角点。理由是厂商 GEMM 太小时效率掉得快，所以块不能切细。 |
| d | 归约方式 | L 个窗口槽循环复用，`R_RS` 条归约流水线，归约用多少 SM 按"稳态 / 尾部"分开配。 | 不设窗口，等 R−1 份全部到齐后一次求和。 | 角点（L = 1、一条流水线），不是新东西。 |
| e | AG 的方向和栅栏 | **拉**：消费者把各 rank 对称工作区里的数据拷到本地（`dst.copy_(src_ws[...])`）。每次调用先跑 `copy_and_barrier_all_intra_node_kernel`，里面有两次 `barrier_all_intra_node`；ready 数组每次清零。 | **推**：发送方把自己那份推进对端的堆槽。票据单调递增，不用清零，每次调用不设全员栅栏。收到后先从堆搬到普通显存再给 GEMM，因为 DCU 上 GEMM 的操作数不能放在堆上。 | 实现上有真实差别：每次调用没有栅栏，适合训练里每层前向、重算、反向都要反复调用。但"推 + 票据、不设栅栏"本身就是论文 1 RS 侧已有的做法，DX 只是把它搬到了 AG 上。 |
| f | 同步原语放在哪 | 发送方等的是**远端**的 free 标志（`free_flag_bufs[dest_local_rank]`，跨卡轮询）；票据用 `cuStreamWriteValue32` 写到远端。 | 所有等待都只等**本卡**的格子，对端用 SM 原子交换小核远程写进来；票据用 4 B 引擎拷贝。 | DCU 平台规律逼出来的改动：自己的格子自己写会互相死等；`WriteValue` 和前面的 memcpy 不保证顺序，会出现撕裂窗口；等待之后再发引擎 memcpy 会锁住 host。属于工程层面，适合放进实现细节或补充材料。 |
| g | 覆盖面 | 只有推理前向。 | 训练前向 + 重算 + 反向（AG+dgrad、独立梯度 RS），也覆盖 vLLM prefill。 | 场景扩展。机制和 a、e 一致，但"在训练整步里跑通并正确"本身有工作量，也是第 3 节控制面问题暴露出来的前提。 |
| h | CUDA graph | 计时用 graph replay。 | 不能做图捕获（F37：跨卡 DX 图捕获后多流 DAG 被串行化或死锁），全部 eager 执行。 | 平台限制，不是贡献。不过它说明在 eager 训练里，host 发射路径就在关键路径上，第 3.1 节的问题正是从这里来的。 |

### 2.3 对重叠机制的判断

- 继承的：协议骨架（推 + 同流票据 + 单调序号 + 释放后复用 + 置换序发送循环）。
- 角点的：c、d。
- 平台适配的：b、f、h。
- 有一定分量、能在设计一节讲成取舍的：a（厂商 GEMM 不改，用流级同步）和 e（AG 每次调用不设栅栏、改成推）。但 a 在论文 1 的 AR 路径已有雏形，e 是把论文 1 RS 的做法搬到 AG。

所以如果把 DX 当作论文 2 的核心创新，审稿人会说它是 "AnchorOverlap RS 的一个配置，在厂商 GEMM 下重新实现"。再加上 MORI 和 FiCCO 的先例，这一条站不住。

## 3. 论文 2 独立成立的部分

下面这些论文 1 没有，也不是对论文 1 换个配置能得到的。

### 3.1 控制面定律：算子级赢不等于整步赢（F49–F51）
- **现象**：融合 AG 单独测 1.29×，但 27B 训练里四处全开（fbc）比只开 RS 组（fbag）慢 3.05%。同一个 70B，MBS8 开 AG 赚 1.68%，MBS4 亏 2.21%，MBS2 亏 4.77%。
- **机理（F50）**：本平台上，拷贝引擎往另一个进程的显存写数据时，host 会被拉回到 GPU 进度附近，约拉回 GPU 落后量的 25%。这和拷贝次数、大小、分叉写法、用哪个 API 都无关。AG 先推后算，所以每次调用都把 host 的提前量清零，GPU 随后空等；RS 先算后推，这个代价被它自己的 GEMM 盖住了。
- **三种改法都无效**：槽位多份、换等待流、改分叉写法，位级都正确，整步都没变好。所以这是平台代价，不是 bug。
- **论文 1 为什么看不到**：评测是孤立算子加推理 prefill 的 graph replay，host 不在关键路径上。

### 3.2 预测器：决定开不开、在哪开（whether / where），不是怎么开（how）
- 论文 1 的配置搜索默认总在重叠，只调粒度、窗口和 SM 配额，而且靠在线短测。我们在本平台上发现，在线测本身会改变后续速度（F44：对称堆上下文一旦建立，释放后也会持久影响引擎操作），所以只能离线预测。
- 第一级是算子级代价模型，带安全门；留一模型检验 0/97 格比原版慢，拿到事后最优收益的 83%。
- 第二级把控制面项写成"空等 e 随每层周期 GPU 时间 D 变化、超过截止点后为 0"。8 卡样本内 5/5，留一 4/5，16 卡样本外 2/2，而且 27B 和 70B 的最优配置正好相反。
- 局限：推理上第一级偏保守，单机比四处全开少 8–10%，双机少约 3%。这一点要如实写。

### 3.3 训练整步与全栈评测
- Megatron 27B / 70B，8 卡和 16 卡（两机 RDMA），对空对照 1.054–1.079×。
- vLLM 完整 LLaMA3-70B：8 卡 1.14–1.17×，16 卡 TP8 × PP2 1.19–1.22×，输出逐 token 一致。

### 3.4 MoE 的控制面对照（支撑论点，不单列贡献）
- 只换数据面，MoE 整步变化 −13% 到 −18%；把控制面（每层两次 `.tolist()` 的 host 同步）也去掉，整步快 11.5%。
- 免同步 a2a 本身有 DeepEP / MORI-EP / HybridEP 先例，所以论文里写成一个框架实例。

### 3.5 厂商 GEMM 不改（设计约束）
这是一条约束，不是新机制。它的意义在于让方法能直接用于训练和现成框架。BW1000 上的对照数据（S18）只能写成"在本平台、Triton 3.3 上的测量"，不能拿来否定论文 1 在 K100_AI 上的结果。

## 4. 论文 2 怎么写才能独立

- **论点**："重叠在训练整步里的收益由控制面决定；我们给出定律并据此预测每个调用点开不开。"不写"我们提出了一种新的重叠方法"。
- **贡献（3 条）**：
  1. 控制面定律（F50）及其测量方法；
  2. 两级预测器：算子级代价模型 + 整步控制面项，离线、训练前决定；
  3. 训练整步、推理、MoE 在 8 卡和 16 卡上的全栈实现与评测。
- **设计一节**：用一段话说明重叠机制沿用论文 1 的票据交接协议，并列出这次的取舍：生产顺序从对齐改为旋转（理由是置换律）；GEMM 交接从内核内信号改为流级（理由是厂商 GEMM 不改、要覆盖训练反向）；AG 从拉加栅栏改为推且不设栅栏。2.2 节表里的 f、h 放到补充材料。
- **评测**：把论文 1 的 RS 形态（或它在 DCU 上的移植）当作一个基线或消融，和 FiCCO 式扇出调度、Async-TP 放在一起比，不单开对比节。
- **风险**：同一组作者两篇都讲"票据交接重叠"，可能被质疑切香肠或自我抄袭。规避办法：两篇的论点不同（论文 1 讲怎么重叠，论文 2 讲开不开）；论文 2 的贡献列表里不出现重叠协议；论文 1 在双盲期间按第三方文献引用。
- **如果想让"重叠机制"也成为论文 2 的贡献**：要在机制上解决 3.1 节的控制面问题。例如推送改成 SM 拷贝核或设备端发起，让 host 不再被拉回，并证明这样做之后融合 AG 在整步里也赚。那会是一个论文 1 没有的新机制。目前只有方向，没有实验。
