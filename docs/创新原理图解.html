1　一次 GEMM+ReduceScatter：串行 vs 分块直推

Row-parallel 层（o_proj、fc2）算完 GEMM 后要做 ReduceScatter（RS）：每个 rank 把输出切成 8 份，第 d 份要和其他 7 个 rank 的第 d 份相加，结果留在 rank d。原版先算完整个 GEMM，再调 RCCL 做 RS，两段串行，而且 RCCL 的内核本身也占 CU。

我们把 GEMM 按输出行切成 8 块，先算要发给别人的 7 块，每算完一块就交给拷贝引擎（DMA，不占 CU）推到它的归属 rank，本地那块最后算。传输于是藏在后面几块 GEMM 的计算时间里，最后只剩一次 fp32 求和。

数字：70B 形状 M32768，rank0 实测（F6）。串行总时长 10.14 ms 为实测；串行内部 GEMM / RS 的切分是示意。我们一侧的块内 GEMM 合计 7.07、等到达 0.07、求和 0.58 ms 为实测。块 GEMM 比整块慢约 10–14%，原因是并发拷贝抢显存带宽，这是重叠付出的代价。

2　架构：和 FlashOverlap 正好反过来

FlashOverlap / flux 的思路是改 GEMM 内核（CUTLASS 里给 tile 分组、重排、每组完成发信号），通信直接调现成的 NCCL。我们反过来：GEMM 一行不改（vendor 库当黑盒，在调用层切块），换掉的是通信，改成对称堆单边推送 + 拷贝引擎 + 流上的条件等待。

这样选是有平台依据的：DCU 上 vendor GEMM 约 361 TF，Triton / 手写 GEMM 只有 106–172 TF（差 2–5×）。凡是要改 GEMM 的方案，在 DCU 上先输在 GEMM 本身；三个开源方案移植过来只有 0.3–0.9×。

3　为什么按"置换序"推：同一时刻，每个目的地只收一份

8 个 rank 每人要把 7 块分别推给 7 个对端，一共 7 步。按 rank 序（大家都先发 0 号、再发 1 号……）时，第一步 7 个人同时往同一个目的地写，形成 incast（多对一）。按置换序（第 j 步发给 r+j）时，每一步每个目的地恰好只收 1 份。

实测（F2 / F7）：8 卡同时按置换序推，对任意对端都是 139–143 GB/s/rank，和对端是谁无关；改成 incast 发送序后，孤立测慢 10–19%，流水线中慢 30–70%。旧说法"8 卡单播扇出墙 17–25 GB/s"其实是 incast 造成的。

先例：AMD MORI 的 gemm_ar（2026-09-17 公开）用 `+rank` 旋转避免多个 rank 同时写一个目的地，属于同一设计动机，论文必须引用。我们补上的是交换机拓扑上的实测定律（任意对端同带宽，只有 incast 慢）。

4　有 rank 迟到时：只等落后者那一块

训练里各 rank 进入同一个 op 的时刻不一样。设最慢的 rank 晚了 δ。原版 RCCL 是集合操作，全员要等它，δ 几乎全额转嫁（实测斜率 0.96）。我们只有"落后者推来的那一块"会晚到，其余 6 块照常到达，前面块的 GEMM 能把这段等待遮住。设能遮住的时间为 W，

曝露 = max(0, δ − W)

W 取决于消费顺序：固定顺序时 W ≈ 1.1 ms；把落后块排在最后消费，W 扩大到剩余 6 块 GEMM 的时间，约 2.5 ms。


直线是模型（斜率与 W 由 F11 的 X2 实测拟合：70B gate_up M8192，迟到 rank3，两轮）。实测点：δ=2000 µs 时，固定序曝露 0.86 ms，最后消费曝露约 0；原版从 4.45 涨到 6.37 ms。

车内实测迟到分布（F13，27B，14.7 万个 op）：p50 156 µs，p90 555 µs，p99 1686 µs，96.7% 的 op 落在 W_fixed 以内。也就是说车辆里大多数偏斜已经被结构性吸收。迟到者每次都不同（自相关 −0.011），所以"预测谁迟到"没有用，这条路线已经降级。

6　为什么孤立测赢、进了训练反而输：控制面

列并行融合（位置④）在 27B 上孤立测 QKV 1.29×，车内单个 op 的设备时间也确实更快，但整步慢了 1–3%。原因在 host：拷贝引擎要 host 先定好字节数再入队，融合调用每次要发约 60 次 host API。车里引擎队列满了以后会反压 host，再加上跨 rank 的 ack 链（我等对端 ack，对端的 ack 又要等它自己的 host 发完被堵住的 push），host 入队时间被拉长到超过设备时间，GPU 就开始空等。

27B 车内实测（F17 / F19），每个调用的中位数。同样一次 42 MB 的 push，空闲设备上 host 只花 0.056 ms，在车里却要约 0.6 ms。push 本身不慢，慢在队列反压和 ack 链。

表格视图

另外两处独立测到的控制面损失：RCCL 为可变 splits 自己要多付 0.56–0.73 ms（count 交换 + host 同步）；Megatron MoE 每层 a2a 前有一次 D2H 同步，host 每层阻塞 17.7–22 ms。所以我们把控制面列为计算争用、传输、同步等待之外的第四类损失。

7　整步分派器：按形状决定开哪些融合

最优配置随形状变：列并行在 27B 整步输 1–3%，在 70B 同批赢 0.58%。静态规则管不住这种情况，所以在训练开头直接用整步时间做决定。

  1. 预热 2 步，所有路径建好上下文、编好内核。
  2. 从全关开始，依次打开 row → bwd → col。每个候选测一次，保留的条件是步时比当前最好的低 0.3% 以上。
  3. 每次探测 = 3 步：第 1 步切换配置，后 2 步流水运行并计时，只在边界同步。各 rank 取 MAX 后统一决策，所有 rank 的开关完全一致。
  4. 没被选中的路径释放它的对称堆和流，并恢复原版函数（F29 修复，见下）。

已知缺陷与修复

27B 上第一次选对了（row+bwd，关 col），但选完后比同批手动设成同配置的 fbag 慢 2.4%；之后两次复跑干脆选错，误开了 col（F31）。诊断（F29）：

  • 预热全开后直接钉成同配置：慢 2.6%。所以问题不在探测本身。
  • 预热时不开 col，再钉成同配置：慢 0.6%。
  • 结论：col 关掉后，它的上下文仍常驻，占约 2.0%；包装层和其余部分约 0.6%。

同一个残留也会污染决策：col 上下文常驻时，每个"不开 col"的探针都被拖慢约 2%，col 看起来像白送。所以光是"丢弃时释放"不够。修复改为预热不开 col，到 +col 探针时才建它的上下文，丢弃时释放。验证批在跑，通过门：两次都丢 col，且选后与同批 fbag 差 ≤0.5%。

探针协议定律待验证：设想是"单次同步迭代从空队列起跑，看不到稳态下 host 入队慢于设备时造成的空泡，会高估入队重的路径"。它的原始依据（F25）后来被更正作废。10-31 的对照批被上面的残留问题混淆，无法判定，修复后再测。
