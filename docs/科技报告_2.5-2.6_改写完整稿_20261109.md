## 第二部分　2.5 节完整稿

# 2.5 分布式自动并行技术

在前述统一计算图建模、多级子图组织、自适应映射与分布式训练策略自动搜索（2.1–2.4 节）的基础上，本阶段将上述能力集成为面向真实训练任务的分布式自动并行框架，并完成两项关键推进：其一，框架前端对接生产级分布式训练引擎 Megatron-LM，形成从声明式配置到可执行启动脚本的自动下放链路；其二，将原依托单一海光平台的适配能力扩展为覆盖四家国产加速卡的多厂商自动检测适配机制，使并行策略搜索、代价模型与脚本渲染在异构厂商软件栈之间复用同一套核心代码。

【图7　分布式自动并行框架整体架构（更新版）】

框架整体分为四层：前端适配层提供统一编程接口，接收用户的模型定义与并行意图；统一建模层承载计算图、多级子图与分布式属性（沿用 2.1、2.2 节方法）；策略层调用 2.4 节搜索方法生成并行计划；执行层则按目标后端分两路下放——面向 PyTorch 后端直接完成计算图切分与运行时调度，面向 Megatron-LM 后端则渲染出可直接在集群上执行的训练启动脚本。运行时调度沿用前期设备子图／服务器子图两级组织与循环依赖修正方案，本阶段不再展开。

## 2.5.1 统一编程接口与双后端下放

框架向用户提供基于 Python 装饰器的 parallelize 编程接口：用户以少量标注声明训练意图（模型路径、目标卡数、并行偏好、序列长度等），被标注函数在首次触发时自动进入"环境检测—策略搜索—脚本生成—任务下放"流程，无需手写设备切分、通信调用与调度代码。相比前期接口，本阶段将配置项从集群信息、并行模式扩展至搜索策略与工程执行两个维度，如表4所示：搜索维度支持流水线并行上限（search_max_pp）与策略偏好；执行维度支持后端选择（PyTorch／Megatron-LM）、运行模式（仅规划／下放生成脚本／直接启动）、数据与精度配置，以及面向多厂商的适配档覆盖（详见 2.5.2）。

表4　自动并行接口主要配置项（更新版）

| 配置项 | 功能描述 |
| --- | --- |
| model_path / num_devices | 模型目录与目标设备数量 |
| parallel_mode | 并行模式：MODEL_PARALLEL、DATA_PARALLEL 或 AUTO |
| search_strategy / search_policy | 策略搜索算法与偏好（如通信优先、吞吐优先） |
| search_max_pp | 流水线并行搜索上限 |
| backend | 执行后端：PYTORCH、MEGATRON |
| run_mode | 运行模式：PLAN（仅规划）、LOWER（生成脚本）、LAUNCH（直接启动） |
| sequence_length / train_iters / lr 等 | 训练配方配置 |
| AUTOPLAN_VENDOR（环境变量） | 厂商适配档显式覆盖，供无厂商硬件环境做跨厂商纯规划 |

面向 Megatron-LM 后端的下放链路为本阶段新增：框架首先读取 HuggingFace 格式模型权重与配置，自动探测模型结构特征（层数、隐藏维度、注意力分组、旋转位置编码比例、查询键值偏置等），据此构建并行搜索输入；策略搜索在张量并行、数据并行、流水线并行等多维空间内枚举候选，以显存可行性为硬约束、以通信与墙钟估算为优化目标选出方案；渲染模块将方案转写为 Megatron 命令行参数与 torchrun 启动脚本，连同权重格式转换说明、断点续训配置一并落盘。该链路使百亿级模型的分布式训练从"人工翻译并行论文参数"转变为"声明式配置直接产出可执行脚本"，并天然衔接"规划—实测—回填—再规划"的代价模型校准闭环（实测常数回填后重新规划即得改进方案）。

## 2.5.2 多厂商自动检测与厂商适配档机制

国产加速卡阵营中，海光（DCU/ROCm 系）、沐曦（MACA）、摩尔线程（MUSA）、天数智芯（CoreX）四家平台的设备接口、通信库、算子库与 Megatron 适配形态各不相同。若对每家维护一套框架副本，核心算法的四路分叉将随演进迅速失配。对本框架四个厂商版本核心文件的逐行比对表明：检测、类型定义、配置与编译模块在各版本间完全一致，真正携带厂商信息的差异集中于搜索、渲染、环境与下放四个文件的少量语句，且内容高度同构——均为"该厂商使用哪个脚本、是否支持某特性"的取值差异。

据此，本阶段将全部厂商差异从代码分支重构为数据字段，建立厂商适配档（vendor profile）机制。每家厂商对应一条档位记录，字段涵盖：环境激活脚本与运行包装器路径、并行能力位（如是否允许序列并行、Transformer 实现是否固定）、设备名前缀、后端显式导入语句、算子库替身目录以及无硬件环境下规划所用的替身卡规格。框架核心在三个固定环节查表取值：其一，规划期按能力位门控候选——对目标平台暂不支持的并行特性，相关候选在搜索期即被拒绝并记录拒绝理由（如序列并行在无配套算子库的厂商强制关闭），使不可行方案在生成阶段即被排除；其二，渲染期将启动脚本中的激活脚本、包装器路径与关键命令行参数替换为档位取值，同一模板渲染出各厂商可执行脚本；其三，下放期按档位切换示例代码的设备前缀与后端注册语句。

档位选择遵循"显式指定优先、自动探测兜底、未知类型回落基线"的规则：环境变量 AUTOPLAN_VENDOR 显式指定优先，供开发机在没有厂商硬件时按替身卡规格做跨厂商纯规划（配错值直接报错并列出可选档位）；真机环境则依据设备名称与 PyTorch 构建版本串自动识别四家平台；无法识别的类型一律回落海光基线档，等价于多厂商合并前框架的既有行为，保证存量环境产物逐字节不变。合并完成后，以基线平台的既有规划产物为基准进行逐键回归比对：搜索结果、中间表示与渲染配置全部一致，仅新增档位标识字段，证明重构对存量链路零扰动。

## 2.5.3 厂商适配包组织与 Megatron 源码自动配置

三家新增厂商的适配资产以自包含目录形式收编：每家包含环境激活脚本、Megatron 挂载引导模块、运行包装器、环境检查工具与调试工具集，脚本内根目录按脚本自身位置相对推导，整目录搬运无需修改路径。四家所接 Megatron 分三种形态：海光采用补丁 wheel 安装进运行环境；沐曦采用厂商官方分发源码原样挂载；摩尔线程与天数智芯采用上游官方干净源码，由引导模块在启动时施加幂等补丁（重复执行不会重复施加，多进程并发启动以文件锁串行化）。对后两家，引导模块进一步实现源码缺失时自动从上游仓库拉取固定版本标签，网络不可达的内网作业机则回落人工放置指引。该组织方式使新增厂商的成本收敛为"一条档位记录＋一个自包含适配包"，框架核心代码零改动。

# 2.6 百亿级参数大模型分布式训练

百亿级参数是检验分布式自动并行技术工程可用性的关键规模：模型参数、梯度与优化器状态的总显存需求远超单卡容量，切分方式、通信路径与数值精度任何一环处理不当都会在训练曲线上留下可观测的痕迹。本节在前期海光平台 Llama2-13B 验证的基础上，将验证范围扩展覆盖四家国产加速卡平台，以统一模型、统一数据、统一训练配方完成跨平台端到端微调对比，并验证多厂商自动检测适配框架在真实训练任务中的有效性。

## 2.6.1 验证任务与统一训练配方

前期工作已在海光 K100 AI 与 BW1000 两平台上，以 Llama2-13B 模型和 BookCorpus 语料完成自动并行分布式训练验证：系统自动完成计算图解析与并行策略生成，模型参数与中间计算分布到多卡执行，训练在 1000 步后进入平稳平台期（后期滑动方差远小于设定阈值，滑动平均一阶导数趋近于零，具体数值【待从旧报告公式对象核对】），未出现误差累积、异常尖峰或发散，证明自动并行链路在国产平台上的基本正确性（图9）。

【图9　前期海光 K100 AI／BW1000 平台百亿级参数模型训练验证（旧图9/10 合并）】

为使跨厂商验证结果可直接对比，本阶段重新设计了统一验证负载与配方，如表5所示。验证模型选用 Colossal-LLaMA-2-13B——在 Llama2-13B 基础上扩展中文词表的开源模型（词表规模 69104），覆盖中英双语文本建模能力；训练数据采用 BAAI Infinity-Instruct-7M 指令数据集约 148 万条（约 6.9 亿 token），单轮完整训练（一个 epoch）折合 1250 步。三家新增平台刻意对齐全部训练超参数：bf16 混合精度、序列长度 2048、全局批大小 256、学习率 1e-5 余弦衰减至 1e-6（预热 200 步）、分布式优化器、全层激活重计算。对齐配方的意义在于：各平台损失曲线的起点、终点与整体形态只取决于数值链路的正确性，任何设备接口转译、算子替换或精度路径的错误都会以曲线偏移、尖峰或不收敛的形式暴露，从而将"训练能跑通"提升为"数值链路正确"的可比证据。

| 天数智芯 | 天垓150 32GB×8 | CoreX 4.4.0（CUDA 兼容层，torch.cuda 原生可用） | 上游官方 Megatron-LM 0.14 干净源码＋6 处幂等补丁 |

（表中"幂等补丁"指重复执行不会重复施加、可安全多次运行的源码补丁；TransformerEngine 简称 TE，为 Megatron 依赖的融合算子库。）

四次移植呈现稳定的同构结构：框架核心的设备检测、策略搜索与脚本渲染完全不感知厂商、四次零改动；每家新增五个标准组件（环境激活脚本、Megatron 挂载引导、运行包装器、TE 替身目录、数据与权重工具链）；厂商间真实差异收敛为三类——Megatron 形态与补丁清单、分布式参数注入方式（新版 Megatron 不识别旧版显式分布式旗标，由运行包装器统一剔除、改用 torchrun 环境变量注入）、设备层方案（兼容层直用或私有后端桥接）。

各平台代表性工程问题及解决途径如下。沐曦平台：编译 C++ 扩展时必须锁定系统 gcc 版本，防止误用兼容层工具链导致符号不兼容；注意力后端相关环境变量不可预置，须交由 Megatron 按命令行旗标自行设置。摩尔线程平台：宿主 CPU 不具备 AVX-512 指令集，TE 与 apex 的融合内核一加载即触发非法指令崩溃（此类硬件级崩溃无法以异常捕获兜底），改为以 TE 替身目录整体屏蔽并在运行前阻断加载；图编译特性在该后端不可用，须在 Python 启动前禁用；实测 TP=1/DP=8 时单卡显存约 76GB、逼近 80GB 上限，据此定稿 TP=4/DP=2（实测约 45GB）。天数智芯平台：32GB 显存放不下 13B 全量微调的优化器状态，实测 TP4/DP2、TP8、TP4/PP2、TP2/PP2/DP2 四种纯 GPU 拓扑全部在优化器状态首次初始化处溢出（约 31GB，与卡容量相当），最终采用张量并行 4＋流水线并行 2＋优化器状态卸载到主机内存的方案，稳态显存降至约 6.5GB（峰值 13.7GB）；另定位到厂商版 flash-attention 训练路径数值异常（不开 flash 的链路与 HuggingFace 原始模型前向逐层比对余弦相似度 0.9998，开启后损失停留在随机初始化水平），默认关闭并保留开关。

## 2.6.3 框架跨厂商运行验证

多厂商自动检测适配机制在四家平台完成落地验证。真机环境下，环境检测模块依据设备名称与框架构建版本串自动识别平台类型并选择对应适配档，渲染产物自动携带该厂商的激活脚本与运行包装器路径；开发机环境下，通过适配档覆盖变量按替身卡规格完成跨厂商纯规划，四家平台的规划产物（搜索结果、中间表示、启动脚本、参数配置）均可离线生成并逐项断言。针对每家平台建立回归驱动，固化三组检查：基线平台渲染产物与合并前逐键一致、序列并行等能力位按平台正确生效、声明式前端在全链路（配置—搜索—渲染—脚本落盘）上产出预期厂商脚本。

在沐曦平台上，框架对 Qwen3-14B（147 亿参数）完成检测—搜索—渲染全流程演练：系统自动探测 8×C500 环境，搜索选中 TP4/DP2 方案（显存估算 59.68GB，对 64GB 卡余量 3.17GB），24 条不满足显存硬约束的候选均附拒绝理由记录，最终产出可直接执行的启动脚本。此外，各平台均以小模型完成声明式链路双卡端到端冒烟（摩尔线程 420 万参数 tiny-llama、天数智芯 OpenLLaMA-3B），摩尔线程平台另设 13B 前向加反向闸门验证（不构建优化器，规避单卡百 GB 级优化器状态限制）。

## 2.6.5 小结

本节完成了分布式自动并行技术在平台广度上的验证：依托多厂商自动检测适配框架，同一套核心代码覆盖海光、沐曦、摩尔线程、天数智芯四家国产加速卡平台，以统一模型、统一数据、统一训练配方完成 13B 全量微调跨平台对比，各平台损失曲线收敛至一致水位，证明移植后数值链路正确、框架的厂商差异收敛机制有效。上述结果与前期海光平台验证共同表明，自动并行方法能够支撑百亿级参数模型在国产算力环境中的分布式训练，并为后续向更大参数规模、更多并行维度与更多厂商接入的扩展提供了框架基础。
