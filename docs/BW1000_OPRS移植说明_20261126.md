# BW1000：OPRS 的 Hygon 移植说明（2026-11-26）

这份文档回答三个问题：NVIDIA 侧的 OPRS 框架搬到了海光栈的哪些文件里；在 8 卡上怎么跑；单卡上验证到了哪一步、
还差什么。需求与规则来自 `docs/BW1000八卡_OPRS迁移与实验交接_20261126.md`（下称"交接文档"）。
单卡阶段的全部原始记录在 `results/bw1000_oprs_20261126/`（先看 `report.md`，再看 `status.md`）。

## 0. OPRS 是什么

OPRS 是"按调用点选路径"的一套框架。先固定**一个**外部重叠后端 B（Async-TP 或 Triton-distributed 二选一），
对模型里的四个张量并行调用点（`qkv`、`proj`、`fc1`、`fc2`）逐个预测：走原来的串行路径、走 DEO（海光自己的重叠方法，
NVIDIA 侧叫 DX）、还是走 B，哪个更快。预测结果写成一份 JSON 计划；运行时派发器在 Megatron 或 vLLM 里照计划执行，
并报告每个路径实际命中了多少次、回退了多少次。

和旧系统的关系：旧的 `planner/` 与 `e2e/megatron/run.sh`、`e2e/vllm/vllm_sp.py`（旧的 `plan` 臂）一个字节都没有改，
它们是另一套系统。OPRS 是并行的一套新入口，两边的计划文件互不兼容（加载器会拒绝）。

## 3. 几个约定

- **臂名到计划文件**（`stowaway/oprs/arms.py`，两个框架叫法不同，指的是同一样东西）：

  | Megatron 的臂 | vLLM 的臂 | 计划文件 | 含义 |
  |---|---|---|---|
  | `serial` | `stock` | 无 | 原来的框架，不挂钩子、不分配对称堆 |
  | `null` | `sp_rccl` | `null.json` | 挂钩子、分配计划里的上下文，但一处都不替换。vLLM 里它就是"序列并行形态 + 全部走 RCCL" |
  | `always_deo` | `all_deo` | `always_deo.json` | 四处能用 DEO 的地方都用 DEO |
  | `always_<B>` | `all_<B>` | `always_<B>.json` | B 能支持的模块用 B，其余串行 |
  | `oprs` | `oprs` | `oprs_<B>.json` | 预测器逐站点选 |
  | `oprs_deo_only` | 同 | `oprs_deo_only.json` | 没有 B 可用时的二选一计划 |

  驱动脚本的臂写成 `名字:种类`，名字末尾的数字是轮次（`s1`、`s2`），比值按轮次配对。
- **不覆盖**：采样目录、计划集目录、结果表都已存在就拒绝写入。重测去新目录。
- **两种数据类别不混**：旧表（`planner/data/cells.json`，标签 `legacy`）和新协议的采样（`b2b16`）路线不同，
  不能放进同一次拟合，汇总里也从不合在一起平均。
- **退出码**：带引擎世界的 Megatron 臂，进程不做 `MPI_Finalize` 就离开，mpirun 自身恒返回 1。臂的真实退出码是
  rank 日志里的 `EXIT n`，驱动脚本记成 `py_rc`，表格工具读它。
- `SW_NP`（或 `NP`）必须在 `source env/env.sh` **之前**设好，env.sh 默认按 8 卡。同一时间只能有一个 `mpirun`。

## 4. 在 8 卡上怎么跑

```bash
cd /root/private_data/stowaway
python3 -m pytest tests -q                                    # CPU，约 20 秒
NP=8 bash bench/run_oprs_smoke.sh                             # 运行时冒烟，不计时
D=results/bw1000_oprs_$(date +%Y%m%d)                          # 新的结果目录；下面的 $D 都指它

# (1) 算子级采样：首批 21 个形状；之后在同一目录里 RESUME 补到 99 点（已完成的点自动跳过，不会重复测）
OUT=$D/raw/operators/tp8_batch bash bench/run_oprs_matrix.sh --first-batch
RESUME=1 OUT=$D/raw/operators/tp8_batch bash bench/run_oprs_matrix.sh --table
OUT=$D/raw/operators/tp8_sites_bw27b  bash bench/run_oprs_matrix.sh --sites bw27b_train
OUT=$D/raw/operators/tp8_sites_llama70 bash bench/run_oprs_matrix.sh --sites llama70_infer
python3 -I tools/oprs_tables.py operator $D --tp 8 --topology BW8

# (2) 新协议下的留族验证（至少要有 5 个模型族的样本；表格里出现 family_holdout_b2b16 的行）
python3 -I tools/oprs_tables.py choices $D --tp 8 --topology BW8 --data $D/raw/operators/tp8_batch/samples_*.jsonl

# (3) 计划集：一个部署围绕一个 B。训练负载 M = seq × mbs = 32768；推理负载 M = 16384
S=$D/raw/operators/tp8_batch/samples_*.jsonl
python3 tools/oprs_plans.py $D/plans/bw27b_async_tp     --tp 8 --backend async_tp     --workload bw27b_train   --data $S
python3 tools/oprs_plans.py $D/plans/llama70_triton_dist --tp 8 --backend triton_dist --workload llama70_infer --rows 16384 --data $S

# (4) 计划的实际派发路径：每个非串行站点经真实派发器计时，与离线预测对照
OUT=$D/raw/operators/tp8_plan_bw27b_async_tp bash bench/run_oprs_matrix.sh --plan $D/plans/bw27b_async_tp/oprs_async_tp.json

# (5) Megatron 端到端：五个臂、两轮（ABAB）
NP=8 SW_MODEL=27b PLANS=$D/plans/bw27b_async_tp \
  ARMS="s1:serial n1:null d1:always_deo a1:always_async_tp o1:oprs s2:serial n2:null d2:always_deo a2:always_async_tp o2:oprs" \
  bash e2e/megatron/run_oprs.sh

# (6) vLLM 端到端（默认五个臂两轮）与自然文本检查（Llama3-70B 真实权重）
NP=8 PLANS=$D/plans/llama70_triton_dist bash e2e/vllm/run_oprs.sh
NP=8 VS_GATE=1 PLANS=$D/plans/llama70_triton_dist bash e2e/vllm/run_oprs.sh
```

Megatron 与 vLLM 的驱动在最后调用 `tools/oprs_tables.py` 写汇总（`summary.md`），采样驱动自己打印每条记录的状态。臂名可以任意起（`名字:种类`，或 `名字:计划文件路径`）。
对称堆大小默认由 `tools/oprs_heap.py` 按计划集算（最大的计划 × 1.25 + 1 GiB），也可以用 `OPRS_HEAP` / `VS_HEAP` 指定。

(2) 与 (3) 的顺序不能反：没有测过的方法不能当候选（计划生成会直接报错）。B 选哪个由 (1)(2) 的数据说话；
Triton-distributed 在 bw27b 上只有 2/4 站点能跑（见 `results/bw1000_oprs_20261126/status.md` 第 1 节），bw70b 与 llama70 是 4/4。

交接文档第 6 节的消融，现在有的和没有的：
- 有：固定 DEO、固定 B（恒定选择臂）；"只用岭回归"对"加残差修正"（算子级，`choices` 表里的 `base_ridge` 与 `oprs` 两行）；
  预测计划对事后最优（算子级，`oracle` 行）；计划的实际派发路径（`--plan`）；生成、加载、每次路由决策的开销。
- **还没有入口**：只用岭回归的计划导出、事后最优计划的导出——也就是这两项消融的端到端版本。两者都要等 8 卡的站点实测数据，
  等数据出来再补 `tools/oprs_plans.py` 的两个选项。

## 5. 移植中确立的做法（都有对应的测试或原始记录）

1. **留族的键是模型族。** 评估代码原来"按模型名留出、按模型族过滤"，旧表里两者恰好相同所以没暴露；模型名与模型族
   不同的数据上会把留出的族漏进它自己的拟合。已修，并有"留出的族从不进入自己的拟合"的结构性测试。
2. **计划条目的字段是严格的。** 加载器只认 `site, op, M, N, K, choice, predicted_log_speedup, scores`；来源层名等放进 `provenance`。
   第一次在框架里加载就死在这里。
3. **Null 计划要带上来源计划的后端。** 它分配的是预测计划的上下文；不带上后端，加载器会拒绝其中 B 的上下文。
4. **"本进程允许哪些方法"的默认值是全部已接入的方法，DEO 在内。** 这个选项叫 `methods`，不叫 backends。
5. **TP=1 时序列并行布局与普通布局是同一组张量。** Megatron 在 TP=1 会自己关掉序列并行（参数校验、层、模型配置三处），
   强行打开会被模型配置拒绝；所以派发条件写成"序列并行形态，或 TP=1"。TP=1 的计划只用来检查通路，永远不是测量臂。
6. **训练结束后的评估也走挂钩子。** `train()` 返回时先打一份报告，进程退出时把增量再打一遍（`after_report` 行），
   对日志求和就是整个进程的计数。
7. **形状落在拟合样本范围之外时，预测是外推。** 计划文件记录越界的维度（`provenance.out_of_range`）。单卡上实际派发路径的
   预测 1.2 对实测 0.4 就是这样来的（`status.md` 第 2 节）。
8. **离线工具不碰加速卡。** 第一次 HIP 调用在这台机器上要 14 秒，曾被记成"生成计划用了 14 秒"。现在导出计划时设备信息取自
   采样记录；`git status` 的耗时也移到计时之外。
9. **vLLM 每个计时格之前先做一次不记录的预热。** 换了一条执行路径之后的首次使用有一次性开销（单卡上见过 1.04 秒对 0.012 秒）。
10. **占位权重会让数值检查变成空结论。** `load_format=dummy` 让模型的输出分布均匀到 1e-5；单卡检查改用带种子的随机权重
    （`VS_SEEDED_WEIGHTS=1`）。
11. **与厂商 GEMM 是否逐位相同，取决于框架怎么存权重。** 见 `results/…/report.md` 的观察 2 与 `bench/oprs_bitwise.py`。
