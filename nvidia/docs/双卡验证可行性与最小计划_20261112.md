# 双卡验证可行性与最小计划

当前机器仅有 1 张 A800。两张 A800 可以为预测器补充新的、同一机器同一口径的多 GPU 算子数据，但不要求一次编译和测试四个仓库。下表依据各仓库 README 与测试入口；是否能在当前软件环境直接运行，仍需实际验证。

| 对象 | A800 / 双卡现状 | 处理优先级 |
|---|---|---|
| Stowaway DX | 已有 A800 TP8、99 点；新的 TP2 数据需独立标定。 | 第一：复用现有环境做少量双卡验证。 |
| FlashOverlap | README 明确支持 A800/SM80，给出 `CUDA_VISIBLE_DEVICES=0,1` 的带宽、搜索和测试例子；只支持 M、N 均为 128 整倍数的规则 GEMM。 | CUDA/CUTLASS 对照优先：可预估验证方法内开关与仓库原生 predictive search，受编译环境影响。 |
| Triton-distributed | README 声明支持 SM80，仓库有 AG+GEMM 与 GEMM+RS 测试；每个具体 kernel 是否支持当前设备和 TP2 必须逐项确认。 | Triton 族优先：先复用已有 Triton-distributed/NVSHMEM 环境与少量算子。 |
| Flux | README 提供 SM80 构建路径，已有用户提供的四卡 AG/RS 记录；真实 TP2 支持与本地构建开销需要验证。 | 第二阶段按需要补充，不把四卡数据重复跑一遍。 |
| Syncopate | README 称论文实验为 Hopper，**多数测试假定至少 4 卡，部分用 8 卡**；前端可在 CPU 运行。 | 先检查 CPU 生成和具体 SM80/TP2 路径；不把整库编译或 2 卡可运行当作前提。 |

## 最小实验和节省卡时原则

1. 数据采集按固定方法独立进行，stock 与 overlap 比较在同一硬件、TP、dtype、版本和时序下测量；不在各方法之间混用标定系数。先核实双卡拓扑和实际运行路径。
2. 首选已有真实模型投影形状，优先覆盖不同规模以及预计快、临界、慢的区域，保证所测实现支持这些维度。训练集和测试集按模型或形状划分，测试标签不用于选择阈值；用 16 连发为主，并记录多次独立 benchmark 及原始样本。
3. 与总是 stock、总是启用、已有方法自带的搜索（适用时）及事后最优比较；记录选对率、几何平均 speedup、错误导致的损失及慢于 stock 的点。保留失败和不支持项。
4. 先跑少量 smoke case 验证正确性与依赖，再按阶段增加覆盖。若某项目构建困难或不支持 SM80/TP2，记录原因并转向可运行项目，避免把卡时耗在装环境。
5. 双卡结果仅能说明 TP2 的预测和实际表现，不自动代表 A800 TP8 或四卡；四卡 Flux/FlashOverlap 记录继续保留。不同数据源可以用于分别评估框架接口，但必须单独计分。
6. 只做算子基准并不能证明训练或推理全模型组合预测有效。Llama3-70B 是推理工作负载，Qwen3.6-27B 是训练工作负载；大模型端到端是否能在双卡运行取决于内存、精度、工作负载和框架，不预先承诺。

## 当前状态

这是一份最小可行计划，尚未换卡、编译或跑新多卡实验。现有 99 点 DX 测量与四卡日志不删除、不重做；后端族接口是 CPU 原型，尚未与四个项目形成已验证的实际端到端插件。
