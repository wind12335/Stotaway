# 计算与通信正交分层预测架构

## 目标与边界

一次固定一个用户选择的重叠方法，由该方法自己的预测器决定每个 QKV、o_proj、fc1、fc2 等调用点开启或回退，并在该方法允许时选择内部配置；不跨方法混合 kernel。统一的是表示、特征、训练和验证流程；不同实现、设备及计时口径的参数不能未经验证互借。

**计算实现与通信实现是两个独立维度**。把某个项目简单标成“CUDA”或“Triton”会遗漏 NCCL、NVSHMEM、CUDA copy、SM 直接读写、TMA 的差异；仅标成“NCCL”或“NVSHMEM”也会遗漏 GEMM 内核与资源占用。

## 四层统一表示

1. **上下文层**：GPU、互连/拓扑、TP、dtype、模型调用点、前向/反向/重算、计时模式、预热、软件版本。实际执行与 fallback 必须记录，不只记录项目名称。
2. **计算层**：CUTLASS、Triton dot、厂商 GEMM，以及 tile/wave、分块和 GEMM 运行代价；具体配置属于方法签名的一部分。
3. **通信层**：把 API/算法、内存和传输机制分开记录。例如 NCCL collective；NVSHMEM symmetric memory + SM 远程访问；NVSHMEM symmetric memory + CUDA peer copy；还需信号、同步、网络拓扑和参与的 SM 或 copy engine。NVSHMEM 不总是直接负责每次数据传输，不能把“用了 NVSHMEM 内存”写成“所有通信都由 NVSHMEM 发起”。
4. **依赖和整步层**：AG 通信产生数据后 GEMM 消费，RS 先产生 GEMM 输出再通信；不同 chunk/wave 的依赖决定关键路径。先估计单调用的相对代价，再用真实调用次数与同上下文整步标定的公共/交互残差选同一方法的调用点组合。

## 当前已核实路径示例

| 实测路径 | 计算 | 通信 API / 数据传输 | 内存 / 信号 | stock |
|---|---|---|---|---|
| FlashOverlap TP2 RS，仓库 predictive search | CUTLASS | 分组 NCCL reduce-scatter；GPU 上的 waiting/signaling kernel | CUDA tensor、wave/计数同步 | cuBLAS + NCCL，来源于仓库 baseline |
| DX TP2 AG/RS | `torch.matmul`（厂商 GEMM），Triton 归约 | CUDA 异步 copy 推送 peer；驱动 stream wait | NVSHMEM 对称缓冲提供 peer 映射，ticket/ACK | PyTorch matmul + NCCL |
| Triton-distributed `552fedc` TP2 AG | Triton GEMM，另有 SM copy/barrier kernel | 同机 `cp_engine_producer_all_gather_intra_node`，All2All pull 使用 peer tensor copy | NVSHMEM 对称缓冲与 rank/barrier 同步；copy engine 路径和 SM 路径不能混成一个 | PyTorch matmul + NCCL |

FlashOverlap 不使用 NVSHMEM 作为该算子核心通信手段；DX 也并非“计算完全 Triton”。Triton-distributed 源码中既有 `cp_engine_producer...` 和 CUDA memcpy，又有设备侧 copy/barrier 等路径；具体数据集要绑定实际启动路径，不能只根据 import 或库名称推断。Syncopate 的可选后端更多，A800 TP2 尚未验证，先不伪造标签。

## 可共享的算法骨架

对每个固定的完整执行路由分别训练相对收益模型：

```text
route = (method, compute, transport, memory, sync, actual_path,
         direction, GPU, topology, TP, dtype, versions, timing, config_family)
features = (log M, log N, log K, [log T_GEMM, log T_comm],
            [chunk/wave、资源和信号等可确认的实现特征])
y = log(T_stock / T_candidate)
```

一套共享模型接口可容纳 shape-only 与有组件测量的版本；组件时间未知时不能虚构，也不能把不同基准的通信时间直接代入。每条路由独立拟合和独立留出预测，避免 CUTLASS/NCCL 的系数跑到 Triton/NVSHMEM 上。先用简单的岭回归验证分层接口，再比较分段/依赖模型、历史量化或带不确定度的选择；参数共享或迁移学习只有在严格跨路由测试后才能加入。流水线 `max` 递推已有 FlashOverlap 等先例，不能单独宣称创新。

`orthogonal_predictor.py` 实现完整路由校验、shape-only 或组件输入的回归和开启/关闭接口；缺少整步标定时仍只表示**算子原型**。整步组合继续使用 `backend_family.py` 中对所有出现的签名、workload、交互项的严格验证。两者目前不是线上接入，没有声称具有通用正确率或速度保证。

`predictor_registry.py` 已提供用户提出的模块识别和分发原型：接入层提供真实的 `(method, actual_path, direction, fallback)`，注册表映射到计算/传输/内存/同步能力，再根据完整硬件、配置与计时签名调用已标定模型。当前显式识别 FlashOverlap CUTLASS+NCCL、DX vendor GEMM+CUDA peer copy/NVSHMEM 对称内存、Triton-distributed Triton+CUDA peer copy/NVSHMEM 对称内存；未知路径、fallback 或未注册模型回退 stock。已加入逐形状 capability 证据检查，未知或不支持形状也回退，避免将“识别路径”误当作形状可执行的证明。只支持已核实路径；这还不是可自动扫描任意源码或抓取 GPU kernel 的通用检测器，也没有改动各项目执行器。未来若加入真正 Triton+NVSHMEM put/signal 路径，需新增独立 adapter 和标定，不能套用 Triton+CUDA copy 的参数。

模型支持 JSON 数值参数持久化与校验，不用可执行 pickle；`freeze_route_model.py` 可将单一路由已有数据冻结为带来源 SHA 的算子级模型。已在 DX TP2 RS 上验证保存、加载、注册和预测流程，文件在数据盘 `tp2_dx_rs_route_model_20261112.json`。它是探索性算子模型，不能作为已验证的训练整步模型或隐式接入运行时。

`unified_step.py` 将注册路由模型产生的单调用预测、前后向发生次数和 `backend_family.py` 的整步组合选择连接起来：强制同一方法与运行环境；每个调用点提供匹配形状的能力证据；没有整步公共代价时只选 stock，没有某个 pair 标定时禁止该 pair 同时开启。已用四层 Qwen TP2 随机 mock 训练数据导出并运行 `qwen36_tp2_unified_step_diagnostic_v2_20261112.json`；算子训练排除了目标 M，但目标整步残差使用相同工作负载的实测值，不能称为未见整步泛化。详细对照和限制见双卡实验进度。

现有另一条在线算子级路径：在 Megatron TP2 初始化时各 rank 校验 bundle、集体批量预测已列出的形状并缓存，未列形状回退 stock；4 组随机 mock 训练配对结果 1.0019×，并非整步组合模型或完整 27B。FlashOverlap 和 Triton-distributed 则分别在双卡算子载具中加载统一 route 策略并执行选择，尚未接入这两个仓库的端到端运行。已知形状可以使用同 route 的精确历史测量，再回退 route 模型；已知与未知形状的准确率应分开报告，不能将查表结果作为未知形状预测准确率。

Syncopate 当前仓库 commit `7892aaf` 的 README 将 GPU 论文实验描述为至少 4 卡 Hopper，不能推断其 SM80 双卡内核可直接运行；不编译整个仓库。其 CPU compiler tests 45 项通过，并使用原仓库生成 M2048/K5120 TP2 all-gather 计划，`syncopate_plan_features.py` 从实际 schedule 提取每 rank 的 2 个 wave、2 个块，其中 1 个带 signal 的块、1 个带 signal 的 wave，带 signal 块对应 10,485,760 字节；假设本地输出 N3072 时 GEMM 工作量为 64,424,509,440 FLOPs。signal 本身不证明跨卡接收或具体传输方式，不能据此确定实际 GPU 传输机制、通信耗时或模型收益；这些是候选结构特征，Syncopate GPU 适配及性能预测还未验证。

## 需要的实证

先分别在 DX、FlashOverlap、Triton-distributed 现有双卡记录中进行按物理形状族留一，并比较每方法自己的 always-stock、always-overlap 和事后最优；计算与通信标签均保留。对 warmup=4 与 warmup=32 的 FlashOverlap 分开验证。后续应评估通信侧信息能否在固定标定成本下改善选择，同时复用现有四卡记录，不能通过跨方法混合样本制造更多训练点。只有同一方法的前后向整步数据能验证 E2E 选择。

初步按方向/K/N 族留一，DX 的统一回归：shape-only 118/160、1.081×、31 慢点；增加同形状实测 GEMM/collective 时间 119/160、1.082×、30 慢点；always-DX 125/160、1.088×。组件并非免费，需要额外测量且没有明显带来优势。Triton-distributed 仅 20 条样本时两种特征均 15/20、0.986×、3 慢点，always-stock 为 1×；因此不能把共同接口当成已成功的通用算法。FlashOverlap warmup=32 的 18 点 shape-only 13/18、1.016×、3 慢点，always-overlap 13/18、1.014×；均是开发数据上的探索，未达稳定泛化证明。原始 JSON 保留在 `data/stowaway-nvidia/results`，相关评估脚本为 `validate_orthogonal_tp2.py`、`validate_flash_tp2.py`。
