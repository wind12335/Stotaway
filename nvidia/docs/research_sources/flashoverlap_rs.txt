报错的根因是 reduce_scatter 这条路径里，代码对 tile 数的计算前后用了两套不一致的公式，而
你的这组尺寸刚好触发了这个不一致。
在 tune/search.py:53 里，generate_row_remap_array() 用的是
total_tiles = (M N) // (BM BN)

这是“向下取整”的 tile 数。
但它的调用方 compute_hint_process() 在 tune/search.py:88 里构造 cSeg 时，用的是
TileNum = div_up(M, BM) * div_up(N, BN)

这是“向上取整”的 tile 数。
只要 M 不能整除 BM，或者 N 不能整除 BN，这两个值就可能不相等，断言就会炸。
你的具体 case 是：
    M = 8192
    N = 29568
  配置文件 configs/m8192n29568k8192_a100.json 的第一个候选是 BM=128, BN=256
代进去：
    div_up(8192, 128) = 64
    div_up(29568, 256) = 116
  所以 TileNum = 64 * 116 = 7424
但另一边：
    total_tiles = (8192 29568) // (128 256) = 7392

于是：
    sum(S_list) = 7424
    total_tiles = 7392

不相等，所以在 tune/search.py:57 触发：
assert sum(S_list) == total_tiles
为什么偏偏你这个尺寸会中招：
    8192 能整除 128 和 256
    29568 能整除 128
    但 29568 不能整除 256
所以只要搜索先试到 BN=256 的候选，就会直接报错。fast_search() 在 tune/search.py:452 是从
第 0 个候选开始试的，而第 0 个候选正是 BN=256，所以它还没来得及试后面的
BN=128 候选，就先死掉了。mp.spawn 只显示 “Process 2” 是正常现象，其他 worker 会被主进
程一起 SIGTERM 掉。
补充一点，这个问题只会在 reduce_scatter 路径暴露出来，因为只有这条路径会调用
generate_row_remap_array()；all_reduce 不走这里。

你现在有三个处理办法：
 1. 直接换尺寸，让 N 能被候选 BN 整除。
    例如把 N 改成 29440、29696 这类 256 的倍数。
 2. 临时绕开不合法候选。
    让搜索先跳过 BN=256、只试 BN=128 的配置。
 3. 从代码上修。
    把 generate_row_remap_array() 的 tile 计数逻辑改成和外部一致，或者显式处理最后那一列
    partial tile。

的情况，或者至少先自动跳过这类非法候选，不再因为第一个候选直接崩掉。

• 更准确地说：这是这个仓库当前 reduce_scatter 实现和调优脚本的限制，不一定是
FlashOverlap 这个想法本身的“理论缺点”。

就你现在这份代码来看，确实有明显的整除假设：
    reduce_scatter 路径里，M 至少要能被 world_size 整除，因为输出 D 直接按 M // world_size
    分配，见 tune/search.py:115。
    当前 search.py 的 remap 逻辑默认按“完整 tile”处理，所以一旦某个候选 BM/BN 让边界出现
    partial tile，就可能出错。你这次就是 N % BN != 0 触发了这个问题，见 tune/
    search.py:56 和 tune/search.py:88。
所以结论不是“所有情况都必须整除”，而是：
  对这个仓库当前的 reduce_scatter 调优流程，最好满足 M % world_size == 0。
  对当前会被尝试的 tile 配置，最好满足 M % BM == 0 且 N % BN == 0。
  现在的 fast_search() 没有先过滤掉不满足整除条件的候选，所以会直接崩，而不是自动跳
  过。
这和“FlashOverlap 天生做不了非整除尺寸”不是一回事。更像是：当前实现为了简单和性能，没
把边界 tile 和 remap 的尾块处理补完整。工程上通常有两种改法：
  输入 padding 到合法尺寸，再在外面裁掉。
  代码里显式支持 partial tile，并在搜索时过滤非法候选。
