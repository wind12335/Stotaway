## 2026-11-12：从源码得到的共同结构

1. **依赖决定流水线方向（源码事实）**：AG 先让输入块到达，GEMM 才能消费；RS 要先有输出块，才能发送及归约。Flux 的 AG 用独立流搬运并等待输入，Ampere 的 RS 在 GEMM epilogue 写对端（`/root/data/flux/docs/design.md:8`）；Triton-distributed 在 GEMM 消费者按数据块等待（`/root/data/Triton-distributed/python/triton_dist/kernels/nvidia/allgather_gemm.py:255`）；DX 的两条路径顺序也不同（`/root/Stowaway-NVIDIA/stowaway_nvidia/dx8.py:88`、`:148`）。**推论**：不能只用总字节数和 FLOPs，把 AG 和 RS 当同一条延迟曲线。
2. **分块带来重叠也带来代价（源码事实）**：FlashOverlap 按计算 wave 分组，用 `max` 累计通信与计算并按分组搜索，通信延迟取实测带宽曲线（`/root/FlashOverlap/tune/search.py:180`、`:207`、`:442`）；Syncopate 表示 transfer/chunk 与依赖、tile wave（`/root/data/syncopate/syncopate/communication/descriptor.py:383`；`/root/data/syncopate/syncopate/interface/tile_schedule.py:35`）。**推论**：分块大小、块数、首块、尾块、信号次数和分块 GEMM 效率都是潜在关键特征，但需要该实现实际配置或测量，不可臆填。
3. **资源干扰依实现而变（源码事实）**：Triton-distributed 的 RS 上下文把 SM 在 GEMM 和通信间划分，并按 tile/SM 比裁剪配置（`/root/data/Triton-distributed/python/triton_dist/kernels/nvidia/gemm_reduce_scatter.py:90`、`:708`）；Syncopate 有 copy engine、TMA 和 SM 传输路径（`/root/data/syncopate/syncopate/communication/comm_runtime/communication_context.py:110`）；FlashOverlap 预测中考虑通信预留 SM（`/root/FlashOverlap/tune/search.py:222`）。**推论**：加入后端/SM 占用、波次与带宽共享特征，但没有这些测量时要显式标记未知。
4. **上下文和计算图影响整步（源码事实＋已有结果）**：DX 行投影反向可继续使用 AG+dgrad，列投影的反向有另外的 AG/RS 调度（`/root/Stowaway-NVIDIA/stowaway_nvidia/autograd.py:6`）。因此每个开关影响的不止一次前向算子。A800 Qwen MBS4 前向行 DX 两轮 1.042×/1.030×，加入行反向和独立 RS 后一个跨批对照为 0.995×/0.981×，见 `results/端到端与预测器结果表.md`。**不能由此单独断言控制面或某一个组件是原因**；BW1000 F50 也不应迁移成 A800 定律。
5. **每个方法的可用集合不同（源码事实）**：FlashOverlap 的 `GemmReduceScatterOverlap` 明确使用 `at::Half`/`ncclFloat16`（`/root/FlashOverlap/src/overlap_impl.cu:266`）；其 README 对 M、N 有对齐限制。实际训练可能用 BF16，而当前公开实现未证明该路径可用；AG 前向也不能凭名称推定支持。规划器必须先按实现、架构、dtype、形状、前反向、框架检查可用性，再决定开关。

## 可验证的架构假设（不冒称最优）

选择某一个方法后：静态收集调用点与前/反向次数 → 匹配该方法真实可用路径 → 用可用的单卡 GEMM、已有 TP8 通信标定及该方法的重叠测量预测每点收益 → 枚举四处至多 16 个同方法开关组合 → 用已测整步残差和组合交互修正 → 留一模型评估、保存证据和不确定性。独立 BRS 是单独开关，不能无证据并入任一行投影。

**关键限制**：现在 99 个点只覆盖 stock/DX 的 8 卡前向算子原型；没有 Flux、FlashOverlap、Syncopate、Triton-distributed 的同口径 A800 实测，也没有足以确定各开关交互的 Qwen 整步数据。CPU 上只能做代码、既有数据验证和未标定原型，不能声称预测器已经适配所有系统或整步选最优。

F50 现有 A800 双卡数据在 `results/a800/F50_verdict.md`：按探索性中位数对比没有观察到 BW1000 那种 host 拉回，默认配置出现过一条超 5ms，结论是**初步不支持、非严格判决**；没有覆盖八卡真实训练，不能把第二级修正设为零或声称 A800 的规律已定。

**需警惕的论文重复**：FlashOverlap 已有延迟预测与波次分组搜索；Syncopate 已探索块大小、后端、SM 分配及 tile 顺序。因此“用这些因素预测算子性能”不能自动算新的论文贡献；系统层的调用点选择、跨前后向整步估计及可靠泛化仍是待验证的研究方向。

**输入泄漏修正**：最初版本把留出形状的 8 卡通信时间 C 直接送给预测器，这不是仅靠单卡可获取的部署输入。现已改为仅用每个训练折的通信测量拟合带宽/截距，再对留出形状预测 C；安全门内层各折也分别拟合通信曲线。修正后下表结果不变。仍需注意 G 是该形状已有组件探针输入，部署时须用实际单卡探针提供，不能从留出点的原版/DX 端到端标签推算。

16 连发：原模型 86/99、1.057×、最坏相对最优损失 25.49%、0 格比原版慢超过 0.5%；相对模型 88/99、1.062×、最坏损失 10.34%、但 **1 格比原版慢超过 0.5%**。单次相对模型 74/99、1.065×，原模型 76/99、1.066×。因此相对模型是有潜力的候选，**尚不能替换既有生产规划器**；已经反复研究过的数据也不是独立最终测试集。它只拟合 DX 数据，并不能据此推断其他系统的预测准确率。

16 连发的慢点是 Qwen3-8B、RS、M8192/K1536/N4096：原版 0.8590 ms，DX 0.9479 ms，误选损失 10.34%。明确保留这个负结果。

嵌套留一探索：外层每次留出一个模型，内层在其余模型中选择 ridge、误差分位和 margin，目标为平均对数加速减去超过 0.5% 回退损失的 5 倍惩罚；网格和目标固定在 `planner/original_a800/validate_nested.py`。结果 88/99、1.063×、1 个慢点、最坏损失 10.34%；同外层原模型 86/99、1.057×、0 慢点、最坏损失 25.49%。逐点 `data/nested_exploratory.json`。即使内层加了回退惩罚，该慢点仍存在；已反复研究同一数据，不能把嵌套结果说成独立最终验证，也不能保证新工作负载没有回退。

## 2026-11-12：整步组合原型与可辨识性

新增 `planner/original_a800/combination_planner.py`：每次指定一种重叠后端；单点效应与可选的两点交互可加在算子级增量上，拟合必须来自同一测量上下文的实测整步变化。枚举开关组合时，用观测矩阵的行空间检查指定阶数的模型能否唯一确定该组合的预测值；不可辨识的组合直接不参与选择。当前尚未接入训练或推理。

默认进一步限制为**仅选择该上下文中已实测的组合**；只有显式开启 `allow_model_extrapolation=True` 才允许选择该模型假设下可辨识但未测的组合。这一研究选项没有实测性能保证，不能当作已验证的训练 Plan。

默认选择时直接使用该组合的实测中位 ΔT，而不是用低阶线性模型把已有点重新平滑：组合存在交互时，错误的低阶模型可能把实测更慢的组合拟合成更快。只有研究模式中未测组合才调用模型估计。

该检查只解决**在指定模型结构下的参数可辨识性**，不保证模型结构正确、未测组合实际遵循加法或交互项、也不保证预测精度。Qwen 当前的前向两处、前反向两处和独立 BRS 不是全因子数据，不能从它们推断 QKV、o_proj、fc1、fc2 各自整步收益；独立 BRS 必须视为独立开关。4 项 CPU 单元测试覆盖组合交互、缺失标定、不支持调用点和不可辨识性；Syncopate 自带的 45 项 CPU 规划/编译器测试通过，不代表 GPU 内核兼容 A800。

### 99 形状完整单卡补测与负结果

随后按相同方法测完原 99 个形状：八块/完整 GEMM 之比最小 1.005×、中位 1.173×、最大 1.802×；数据 `/root/data/stowaway-nvidia/results/tp8_20261111/single_gpu_gemm_split_all99_20261112.json`，SHA256 `f9929eb4b983b61aa1910c6299e95a8639e7f46aafbfbd377aacd0dae2c0dbba`。这不是重复 8 卡实验。单卡探针消耗的时间与可能的设备状态差异，今后部署和正式验证都需要计入。

本次 16 连发的完整 GEMM 时间与原 8 卡组件测试中的 G（单次、跨 rank 取最大）相比，中位比约 0.920，范围约 0.805–1.094，二者计时方式与运行窗口都不同。当前原始模型把组件 G 用于 b2b 预测，可能存在输入口径差；不能将差异全归因于单次/连发，也不能直接替换成新 G 后声称提升，需明确部署输入和独立验证。

加入这个**每个留出点也需在规划时实测**的分块特征后，16 连发留一由不加特征的 88/99、1.062× 变成 **85/99、1.059×**，均有一格比 stock 慢超过 0.5%；单次由 74/99、1.065× 变成 79/99、1.069×。详见 `planner/original_a800/data/relative_split_exploratory.{md,json}`。这意味着它尚未改善用户重视的 16 连发目标，不应默认开启；差异也可能受模型、样本和不同时段测量影响，需独立数据复核。

补充探索：99 点分三种算子分别计算分块时间比与旧 TP8 算子 speedup 的 Pearson 相关系数：RS −0.626、AG up −0.737、AG gate/up −0.940，各 33 点。这说明当前数据里分块越亏、DX speedup 趋向越低；但模型/形状和两次不同测量窗口共同影响两者，相关不等于因果，也不意味着额外特征对样本外决策有益（上面的留一结果即为反例）。

三种形状组的分块耗时比中位数：RS 1.114×、AG up 1.251×、AG gate/up 1.129×，各 33 点。分别统计是为了提醒不同投影形状的分块代价不同，并不意味着通信类型本身造成该差异；本探针没有通信。

进一步源码定位：Triton-distributed 当前 AG 在 compute capability <9 时明确走非 persistent GEMM，RS 的 TMA persistent 实现受 `has_tma` 限制、配置搜索在 <9 时只添加非 persistent（`python/triton_dist/kernels/nvidia/allgather_gemm.py:667`，`gemm_reduce_scatter.py:513`、`:736`）。这是源码层面的 A800 可行路径线索，不是本机多卡通过证明。

另一个影响基线比较的事实：该 Triton-distributed 版本的 `gemm_rs_op` 对小 FLOPs、满足其他条件的情况直接回退 `torch.matmul + reduce_scatter_tensor`（`gemm_reduce_scatter.py:636`），因此应记录实际运行路径，不能只凭入口函数名认定实测了重叠内核。Flux 的配置注册表也有“未找到调优配置时回退到首个已注册 hparams”的路径（`/root/data/flux/include/flux/op_registry.h:184`），比较时需要记录选中配置和是否命中调优表。

## 2026-11-12：Qwen3.6 混合注意力的调用点不能仅看名称

本地 Qwen3.6 模型配置 text_config 实际有 64 层：48 层 GDN 线性注意力、16 层 full attention（`/root/eb-public/huggingface-models/Qwen/Qwen3.6-27B/config.json`）。Megatron 实验载具中，GDN `in_proj` 使用 `tp_comm_buffer_name="fc1"`、`out_proj` 使用 `"fc2"`（`/root/data/stowaway-nvidia/third_party/Megatron-LM/megatron/core/ssm/gated_delta_net.py:141`、`:224`）；MLP 自己也叫 fc1/fc2。原有 NVIDIA 适配器 `STOWAWAY_DX_SITES` 只按这些名字筛选（`experiments/megatron_prelude.py:200`）。因此此前的“fc1/fc2 打开”包含 GDN 与 MLP，不能误读为仅 MLP。

当前运行参数 `hidden=5120`、`kv_channels=256`、24 个 attention 头、4 KV 组、GDN key 16×128、value 48×128、FFN=17408、TP8。按代码算出的 GDN 全局输入投影维度 `2×2048+2×6144+2×48=16480`，每 rank 2060；GDN 输出投影每 rank K=768，N=5120。完整注意力的 query 总宽是 6144 而非 hidden 5120，其 QKV 加输出 gate 的总输出宽是 `6144+2×1024+6144=14336`、每 rank 1792；输出投影每 rank K=768。MLP fc1 每 rank N=4352，fc2 每 rank K=2176。上面是源码与参数推出的静态形状，仍须用运行时形状日志核对。

这也意味着原有 dense `planner.py` 中 `head_dim = hidden // heads` 及统一四点公式不能直接套在该 Qwen 载具。要做 Qwen 预测器，需要以层类型和真实维度区分调用点；未来改接入时必须保证所有 rank 使用同一计划，不随单 rank 分支选择。

已实现静态形状清单生成器 `planner/original_a800/qwen36_shapes.py`，保留 `gdn_in/gdn_out/mlp_fc1/mlp_fc2` 等独立逻辑项和现有适配器名称的多对一关系；M8192 示例保存在 `planner/original_a800/data/qwen36_static_manifest_m8192.json`。CPU 测试覆盖维度、层数和非法配置。清单仍是从代码和配置静态推导，未做 8 卡运行时 trace，也不代表这些逻辑项目前可独立部署。

后续版本 `qwen36_static_manifest_m8192_v2.json` 明确记录 BF16、SP、SwiGLU、Megatron local hybrid、全局 M 等假设；对应最新预测输出 `qwen36_operator_exploratory_m8192_v5.json`。这些假设不代表 HF 完整多模态模型的实权重训练。

形状计划入口 `stowaway_nvidia/shape_plan.py` 和 `experiments/megatron_prelude.py` 现可按标签与 M/K/N 区分同名的 GDN、MLP 投影；显式设置 `STOWAWAY_DX_SHAPE_PLAN` 才启用。必须提供手工诊断计划及匹配平台、软件、调度、反向、BRS 参数；各 rank 先交换载入错误和摘要并一致才继续，未列形状回退原版。现仅 CPU 验证解析和规则；因为当前只有 1 卡，还没有验证 8 rank 运行和端到端。

进一步按每类算子标定集的 M/K/N/G/B 范围检查，`full_proj` 与 `gdn_out` 的 K=768 低于当前 RS 训练点最小 K=1280，且 G 也在范围外。v3 计划文件 `qwen36_operator_exploratory_m8192_v3.json` 已显式标注这些外推维度；两个 RS 的相对模型 DX 结论因此尤其不能当作可靠部署选择。范围检查仅是最低限度的外推提示，不代表在各维边界内就有充分覆盖。

v4 增加一个探索性 `cautious_choice`：超出单维范围或两种模型选择不同就回退 stock；当前六处全部回退。此规则只是显式标记不确定性，**既未证明安全，也未利用整步信息，不能据此说 Qwen DX 一定无益**；与已有前向行 DX 的正收益并不冲突，因为后者是整步真实短跑，而这里是两种算子模型预测。

对 99 点已有留一预测额外计算“双模型都选 DX 才选 DX”：16 连发为 84/99、1.055×、0 个点比原版慢超过 0.5%、最坏相对最优损失 25.49%。这比原模型 86/99、1.057× 更保守但没有显示出整体收益优势。因此这种规则仅作 Qwen 未验证范围内的诊断回退，不作为新预测器的性能改进。

### GDN 输出宽度补齐：单卡前向候选

对 GDN 输入投影 `K=5120,N=2060`，BF16、16 连发、8 组随机顺序，单卡将权重输出宽补齐到 2064 后比较原 2060 的 GEMM。M8192 中位 `1.239/0.833 ms = 1.487×`，M16384 `2.362/1.485 ms = 1.591×`；也测了 N=2080/2112/2176。数据 `/root/data/stowaway-nvidia/results/tp8_20261111/qwen36_gdn_padding_single_gpu_20261112.json`，代码 `experiments/qwen36_gdn_padding_probe.py`。补齐后前 2060 列数值通过当前探针对照。

这只是单卡前向 GEMM，输出截取视图不连续，未计入变回连续、真实权重补齐、内存、通信和反向；计时样本也存在明显阶段变化，不可称为训练端到端加速。其实际原因可能是 cuBLAS 内核或布局等选择，当前没有内核分析证据，不能断言原因。

进一步将 padded GEMM 的前 2060 列复制到预先分配的连续张量并计入耗时，单卡中位数：M8192 原 GEMM 1.236 ms、补齐 2064 后 GEMM+复制 0.860 ms，**1.438×**；M16384 分别 2.359/1.605 ms，**1.470×**。数据 `qwen36_gdn_padding_contiguous_single_gpu_20261112.json`，同脚本的独立第二次运行；保留随机交错样本。复制后的输出是连续张量，但仍不含真实模块的 padding 管理、反向、内存分配与通信，不能推导端到端收益。

已有训练日志已用 `planner/original_a800/extract_qwen36_steps.py` 汇总到 `data/qwen36_step_inventory.json`，每个日志有 SHA256、12 步去前三步中位、rank0 前向和独立 BRS 命中。MBS2 完整 fbag/fbc 中 rank0 BRS 为 `layers=0,mappings=192`，MBS4 为 `layers=1548,mappings=192`；即同称 BRS，实际被接管的调用集合也不同。现有表并未提供足够信息把该变化唯一分摊到具体层或整步效果，不能把不同 MBS 当成同一个固定 BRS 干预来拟合。
