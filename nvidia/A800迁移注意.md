# Stowaway A800 迁移注意

写给 A800 侧的执行者（Codex）。11-09 写，依据是本仓库 master 的代码和 `A800双卡环境检查报告.md`。

## 0. 先读这一段

**论文是什么。** 主创新是**重叠规划器**：训练或推理开始前，为每个 TP 调用点（QKV、o_proj、fc1、fc2）决定用不用计算通信重叠、用哪一种重叠。规划器分两级，第一级是算子级代价模型，第二级是整步控制面项。DX 是规划器的一个候选后端，沿用论文 1（AnchorOverlap）的票据交接协议，本身**不是**论文贡献。A800 迁移要回答三个问题：

1. DX 在 CUDA 上能不能位级正确地跑起来。
2. **控制面定律 F50 在 A800 上是否成立。** F50 的意思是：拷贝引擎往另一个进程的显存写数据时，host 会被拉回 GPU 进度附近。这决定论文的论点能写多强，是 A800 上最重要的一个实验。
3. 规划器在新平台上重新标定后，选得对不对；同时把 TE、Async-TP 等现成重叠方法接进候选池。

**不要做的事：**
- 不改 DX 的协议，也不为了 A800 去调优 DX 的调度。机制已冻结，A800 上测到的是什么就报什么。
- 不要动 DCU 路径。DCU 的结果必须仍可由本仓库复现。所有 CUDA 改动加在一个平台开关后面（见 §2），默认值保持 DCU 行为。
- 不要用冒烟测试的数字下结论，冒烟只看正确性。
- 在 `a800-port` 分支上工作，不直接改 master。

**术语：**
- 对称堆：每张卡分配一块缓冲，其他卡可以拿到它的指针直接读写。
- 票据（ticket）：4 B 的单调计数。写完数据后紧跟着写票据，接收方等票据 ≥ 本轮序号再读数据。
- ack：接收方用完槽位后回写给发送方的 4 B 计数，发送方等它之后才复用槽位。
- 置换序：第 j 步发给 `(rank + j) % R`，这样同一时刻每张卡只收一路数据。

## 2. 运行时替换（最小改动）

### 2.1 平台开关和 `hip()` 垫片

加一个环境变量 `SW_PLATFORM=dcu|cuda`，默认 `dcu`。`cuda` 时 `common_ops.hip()` 返回一个垫片对象，方法名保持 `hipXxx` 不变，内部调用 libcudart / libcuda。这样 `gemm_rs_dx.py` 的调用点一行都不用改，DCU 路径也不受影响。DX 生产路径用到的调用只有下面几个（全仓统计）：

| HIP（现用） | CUDA 对应 | 注意 |
|---|---|---|
| `hipMemcpyAsync(dst, src, n, 3, stream)` | `cudaMemcpyAsync(dst, src, n, kind, stream)` | DCU 传 3（D2D）。对端 IPC 映射的指针建议传 `cudaMemcpyDefault = 4`（靠 UVA 判断方向），比较稳 |
| `hipEventCreateWithFlags(&e, 0x2)` | `cudaEventCreateWithFlags(&e, 0x2)` | 0x2 = DisableTiming，两边数值相同 |
| `hipEventRecord / hipStreamWaitEvent / hipEventQuery / hipEventSynchronize / hipEventDestroy` | `cuda` 同名 | 签名相同 |
| `hipMemset` | `cudaMemset` | |
| `hipStreamWaitValue32(stream, ptr, val, flags, mask)`，**5 个参数**，`HIP_WAIT_GTE = 0` | `cuStreamWaitValue32_v2(stream, ptr, val, flags)`，**4 个参数，没有 mask**；`CU_STREAM_WAIT_VALUE_GEQ = 0x0` | 改的是 `gemm_ar_rd._wait_value_gte`。CUDA 的 GEQ 按 `(int32)(*p - val) >= 0` 做环绕比较，票据单调且小于 2^31 时语义一致。ptr 的 argtype 用 `c_uint64`（CUdeviceptr） |
| `hipStreamWriteValue32` | `cuStreamWriteValue32_v2` | 只在 `gemm_rs_dx._write_value`（AG 的可选门）里用到 |
| `hipGraph*`、`hipStreamBeginCapture` | 不迁 | 只出现在非生产路径。DX 是 eager 执行（F37） |

- torch 的 `stream.cuda_stream` 就是 `cudaStream_t`，可以直接当 `CUstream` 传给 libcuda。
- 原型（argtypes / restype）在 `hip()` 里绑定一次，这一点要保留。DCU 上实测每次调用都重新设 argtypes 要多花 10–20 µs。
- **DX 的所有等待都只等本卡上的格子**：到达票据由对端写进来，ack 由对端的小核远程写进来。所以 `cuStreamWaitValue32` 不需要等对端显存，环境报告里测过的本卡写入 / 等待就是 DX 实际用到的形态。
- 可见性：如果 G2 位级门出现撕裂（数据还没落地，票据已经到了），先试给等待加 `CU_STREAM_WAIT_VALUE_FLUSH`（需要设备属性 `CAN_FLUSH_REMOTE_WRITES`），再考虑在数据拷贝和票据拷贝之间加别的屏障。**不要改协议顺序。**

### 2.2 对称堆替换（`pydushmem.DushmemHost`）

DX 只用到四个方法，语义如下：
- `malloc(n)`：集合调用，所有 rank 按相同顺序调用。返回本卡缓冲的 VA。
- `ptr(addr, pe)`：返回本进程里可以用来写 `pe` 那块对应缓冲的 VA。
- `free(addr)`：集合调用。
- `barrier_all()`：全员栅栏，只在建上下文和 close 时用，每次 op 都不用。

**推荐 A：CUDA IPC。** 写一个 `CudaIpcHost` 类，实现上面四个方法：
- `malloc`：用 ctypes 直接 `cudaMalloc`，不要用 torch 缓存分配器的内存，因为 IPC 句柄只能对应分配的基址。
- `cudaIpcGetMemHandle`，在 TP 组内交换句柄。交换走一个 gloo 组的 `all_gather_object`，或者 MPI。
- `cudaIpcOpenMemHandle(..., cudaIpcMemLazyEnablePeerAccess)`。
- `ptr` 查表：`peer_base[pe] + (addr - my_base)`。
- `barrier_all` 用 gloo 组的 `barrier()`。

A 方案依赖最少，2 卡 NV8 上 P2P 已确认 OK。

**备选 B：NVSHMEM**（`nvshmem4py-cu12 0.1.2` 已装）：`nvshmem_malloc + nvshmem_ptr`。节点内 NVLink 上 `nvshmem_ptr` 能返回可直接写的对端指针，更接近 DCU 的 dushmem 形态。缺点是 0.1.2 版本较早，而且论文 1 的原内核（Triton-distributed）也会初始化 NVSHMEM，同一进程里两套 NVSHMEM 初始化要避免冲突。

建议先用 A 把 DX 跑通。§3 的 F50 探针要**两种目的地都测**，见 G3。

### 2.3 引导与启动器

- DCU 的引导依赖 DCU 版 torch 自带的 `torch.libs/libmpi-*.so`：`pydushmem.host.mpi_init()`，再用 `MPI_Comm_split` 切 TP 子组，见 `mgd_tp_patch._bootstrap`。pip 装的 torch 没有这个库，而且 "MPI 必须在 torch 之前加载"（`prelude.py` 的 interposition 顺序律）是 DCU 专属的规矩，A800 上不需要。
- **建议 A800 上去掉 MPI，改用 torchrun 启动**。句柄交换和栅栏都走 torch.distributed：
  - Megatron 里直接用 `mpu.get_tensor_model_parallel_group()` 的 rank 列表，另建一个同成员的 gloo 组。
  - 新建通信组必须**所有 rank 按相同顺序调用 `new_group`**，非成员也要调用，不能提前退出。这是 16 卡上踩过的坑。
- `arm_inner.sh`、`moe_inner.sh` 和 `e2e/vllm/vllm_sp.py` 读的是 `OMPI_COMM_WORLD_*`。改成先读 `RANK / LOCAL_RANK / WORLD_SIZE`（torchrun 会设置），读不到再退回 OMPI 变量。
- vLLM 的 `external_launcher` 本来就是给 torchrun 用的。
- 如果嫌改动大想保留 mpirun，可以在数据盘的 conda 环境里装 openmpi，但 `pydushmem.host.MPI_LIB` 的查找路径要改。二选一，**不要两套引导混用**。

### 2.4 Triton 小核

- `k_dx_sum`（本地块加 R−1 份，一次 fp32 求和）只有普通的 load / store，可以直接移植。
- `kernel_flag_xchg` 是 `tl.atomic_xchg(..., sem="release", scope="sys")`，写到对端 IPC 内存，NVLink P2P 支持 32 位系统范围原子操作。DCU 上 `sys` 和 `agent` 生成的 ISA 相同；CUDA 上 `sys` 会真正生效，比 DCU 更强，没有坏处。
- 预热技巧 `kernel_flag_xchg.warmup(1 << 40, 1, grid=(1,), ...)` 用 `1 << 40` 让指针参数按 int64 编译，因为堆 VA 超过 int32。这个技巧要保留。**同时必须保留 `do_not_specialize=["dst", "val"]`**：DCU 上踩过一个坑，某个内核预热时传了 n=1，被 Triton 特化成常量，结果每次只拷 1 个元素（`rs_relay.py`，审计 #7）。新写的预热调用都要检查这一点。
- Triton 3.4 里 `CompiledKernel` 的调用接口和 3.3 可能不同（`ck[(1,1,1)](dst, val)`、`ck._init_handles()`）。报错了就改成普通的 `kernel_flag_xchg[(1,)](dst, val, num_warps=1)`，功能等价，只是每次发射多几 µs。

**逐轮变异**：所有正确性测试每一轮都必须换新输入。DCU 上证实过，用同一份输入反复验证无效：协议坏了，上一轮的旧数据照样能"对上"（幂等律）。

### G3：F50 探针（A800 上最重要的单项实验）

**它回答什么。** DCU 上，拷贝引擎往**另一个进程的对称堆**写数据时，host 会被拉回 GPU 进度附近，大约拉回 GPU 落后量的 25%。这个现象和拷贝次数、大小、分叉写法、用哪个 API 都无关（F50，`probes/copy_hostblock_heap.py`）。往普通显存写、并用值门控分叉的时候，host 不会被拉回（`copy_hostblock_plain.py`）。融合 AG 先推后算，所以每次调用都会把 host 的提前量清零。这就是"算子级赢、整步输"的机理，也是规划器第二级那一项的物理来源。

**探针怎么跑**（照搬 DCU 的协议，只换运行时）。2 进程，rank0 测量，rank1 空闲：
1. 在流 S 上睡 400 ms，人为让 GPU 落后 host 400 ms。
2. 然后发 40 个 op。每个 op：S 上一个小核，接着分叉到 lane，在 lane 上发 7 次 1 MB 拷贝，每次后面跟一个 4 B 票据。
3. 统计 host 花在每一类调用上的时间。

目的地分 4 类：
- 对端 IPC 内存（cudaMalloc + IPC 打开）
- 对端 NVSHMEM 堆
- 本卡 cudaMalloc
- 本卡 torch 内存

分叉方式有两种：事件门控、值门控。另外，**`CUDA_DEVICE_MAX_CONNECTIONS=1` 和默认值都要测**。

**预注册判据**（写进 `results/a800/F50_verdict.md` 再跑）：
- **F50 成立**：对端目的地 40 个 op 的 host 总时间 ≥ 本卡目的地的 5 倍，并且总时间随睡眠时长同比增长。可以加做一组 200 ms 和 800 ms 的睡眠来确认是否线性。
- **F50 不成立**：对端目的地 host 时间和本卡目的地处在同一量级（< 2 倍），而且 40 个 op 加起来 < 5 ms。
- **介于两者之间**：如实记录比值，不要硬判。

**两种结果怎么处理：**
- 成立：论文的论点直接变成"跨平台都存在"。
- 不成立：规划器第二级在 A800 上应当自动标定成 e ≈ 0。**不要因此去找别的机理来凑。** 但要做 §4 的整步 fbag vs fbc 对照，看 A800 上是不是另有原因导致"算子级赢、整步输"，例如 `CUDA_DEVICE_MAX_CONNECTIONS=1` 的单队列队头阻塞、NCCL 和 GEMM 抢 SM。

## 4. Megatron 训练（端到端）

**Megatron 版本**：用上游 NVIDIA Megatron-LM `571370c`（core_r0.18.0），不要用海光的 Megatron-LM-das 分支。DCU 上 Megatron-LM 是作为 das 的子模块使用的，提交号相同，这样两个平台的训练核心代码一致。

`3rdparty/patches` 里的两个补丁都**不要打**：
- `typing.override` 那个，Python 3.12 自带。
- das 那个（`recompute.py`、`param_and_grad_buffer.py`）是 das 分支专属。上游若同样遇到 `micro_sp_idx_` 的 UnboundLocalError，再单独处理并记录。

**`prelude.py` 要改的地方：**
- `import hcu_megatron.megatron_adaptor`：das 专属，删掉或加 `try` 保护。
- 预加载 MPI（`ctypes.CDLL(_pHost.MPI_LIB)`）：去掉，见 §2.3。
- `WrappedTorchNorm` 的 SP 断言绕过、`enable_hyper_connection` 剥离：先在上游原样跑，报错才保留，并记录原因。
- `mgd_tp_patch._install_autotune` 里 hook 的是 `hcu_megatron` 的 `train_step`。论文的臂不用在线自动调优（`OPUS_AUTOTUNE` 关闭，F44），所以不用管。`_mt.train` 的引导 hook 在上游同样有效。

**`arm_inner.sh` 要改的地方：**
- `HSA_FORCE_FINE_GRAIN_PCIE`、`GPU_MAX_HW_QUEUES`、`DUSHMEM_SYMMETRIC_SIZE / OPUS_HEAP`：DCU 专属，删掉。
- `CUDA_DEVICE_MAX_CONNECTIONS=1`：**保留**，这是 Megatron SP 的要求，DCU 上也设了，两边口径一致。
- `--tensor-model-parallel-size 8`：改成 `${TP:-8}`。
- 其余参数一律不动：seq 4096、全重算、bf16、mock 数据、`--transformer-impl local`、`--overlap-grad-reduce`、分布式优化器、GBS = 8 × MBS。
- `--tokenizer-model` 指向 `/root/eb-public/huggingface-models/Qwen/Qwen3.6-27B`，vocab 248320 保持不变。

**载具（vehicle）配置，与 DCU 保持一致**（来自 `e2e/megatron/run.sh`）：

| 载具 | hidden / ffn / heads / KV 组 | 层数 NL | MBS | DCU 8 卡结果 |
|---|---|---|---|---|
| 27B | 5120 / 17408 / 40 / 8 | 32 | 8（第二级还测过 4） | fbag 对空对照 1.057×；fbc 比 fbag 慢 3.05% |
| 70B | 8192 / 28672 / 64 / 8 | 8（DCU 64 GB 的显存上限） | 8 / 4 / 2 | fbag 1.063–1.077×；fbc 相对 fbag：MBS8 −1.68%（赚），MBS4 +2.21%，MBS2 +4.77% |

- **8 卡阶段先完全照搬上表**，跨平台对比只用这一组。A800 是 80 GB，比 DCU 多，但 70B 也**先保持 NL=8**。放大配置（例如 70B 用更多层）另开一组，单独报告。
- **2 卡阶段只做功能验证和小规模校准**，不出论文数字。TP=2 时每卡的参数和优化器状态是 TP8 的 4 倍，27B 截到 NL=4–8 才能放下，具体按实际显存试出来，并在 ENV.md 里记录。

**臂（arm）**：沿用 `run.sh` 的定义。
- `base`：原版。
- `fnull`：空对照。环境、堆、hook 都一样，但什么都不接管，用来扣掉非重叠因素。
- `fbag`：RS 两处开重叠。
- `fbc`：四处全开。
- `plan`：规划器来选。

每个模型都按 ABAB 顺序跑两遍，取第 3 次迭代以后步时的中位数。

**判决性实验**（8 卡，规划器第二级的跨平台检验）：同一个 70B，在 MBS 8 / 4 / 2 下各比较 fbag 和 fbc，27B 在 MBS8 下比较。
- 如果 A800 上 fbc 相对 fbag 也随 MBS 变号，F50 或另一种控制面代价成立。
- 如果全部同号，就按实测结果写。

## 5. vLLM 推理

- **单独建环境**。vLLM 会锁定自己的 torch 版本，装进训练环境会把 torch 2.7 和 Triton-distributed 的 triton 3.4 弄坏。
- **首选 vLLM 0.11.0**，和 DCU 用的 0.11 同一个大版本，`vllm_sp_patch.py` 就是按 0.11 的 `LlamaModel.forward` 写的。我印象中 0.11.0 要求 torch 2.8，请以 pip 实际解析出来的结果为准。
- **换其他版本时**，要检查 `LlamaModel.forward` 的签名、`aux_hidden_state_layers` 字段，以及 `get_pp_group / IntermediateTensors` 的 import 路径。
- 补丁里 `_w_nk` 同时兼容两种权重布局（das 分支的 [K_in, N_out] 和上游的 [N_out, K_in]）。上游是 [N_out, K_in]，所以走的是 `return w` 这条分支。
- **不需要**：`3rdparty/dcu_shims`（amdsmi / lightop / lmslim 的桩）、flash-attn 的 DCU 专用轮子、`VLLM_USE_OPT_RESHAPE_AND_CACHE`。
- **保留**：
  - `enforce_eager=True`，DX 不做图捕获。
  - `distributed_executor_backend="external_launcher"`。
  - 最后的 barrier 用 `get_world_group().cpu_group`（gloo）。不能在默认 NCCL 组上调 `torch.distributed.barrier()`，DCU 16 卡上它新建了一个通信器，把显存撑爆了。
  - 所有臂用同一个 `gpu_memory_utilization`，保证 KV cache 预算相同。
- **规模**：
  - 8 卡阶段用 `/root/eb-public/huggingface-models/meta-llama/Meta-Llama-3-70B`，80 层全量，TP8，M16384，和 DCU 一致。
  - 2 卡放不下 70B（权重 141 GB，两卡共 160 GB，KV cache 基本没有空间）。2 卡阶段只做冒烟：可以下载一个 Llama 架构的 8B 模型到数据盘，也可以先跳过。补丁只 hook `LlamaModel`，Qwen3 走不到这条路径。
- **臂和门**：
  - 臂：`stock / rccl / dx / plan`。rccl 是 SP 改写后、四处都用原版通信的形态。
  - 输出门：用 `e2e/vllm/vllm_gate.py` 的自然文本门，4 个提示词 × 48 个贪心 token，和 stock 逐 token 比较。**不要用随机 token 当门**：随机 token 下一个 token 的分布太平，rccl 自己都会翻转。

## 6. 规划器重新标定

规划器（`planner/`）的结构不改，只换数据。DCU 的数据留在 `planner/data/`，A800 的放 `planner/data_a800/`，用环境变量 `SW_PLANNER_DATA` 切换。这需要把 `planner.py` 和 `step_planner_v3.py` 里的 `DATA` 改成读这个变量。

- **第一级（算子级代价模型，`costmodel.py`）**
  - 输入是 `cells.json`，每格一条记录：
    - 形状：`op`（rs / ag_up / ag_gu）、`model`、`M`、`N`、`K`
    - `B`：载荷，单位 MB
    - `G`：单卡厂商 GEMM 时间
    - `C`：NCCL 集合通信单独的时间
    - `Cdx`：RS 格才有，我们纯数据面的时间
    - `stock_b2b` / `dx_b2b`：连发计时，连续发 16 个 op 不等待，总时间除以 16，重复 8 次取中位数，取最慢的那张卡
  - `extract.py` 从 `results/raw/ops_8card/*.log` 解析出这张表。A800 的算子矩阵跑完后，产出同格式的 `cells.json` 即可。
  - 每个 op 至少 5 格，否则 `fit` 会跳过这个 op。
  - `planner.py` 里 `R = 8` 写死了，`extract.py` 也一样。改成参数，2 卡标定时用 R=2。
- **第二级（整步控制面项，`step_planner_v3.py`）**
  - 常数：`K_E = 0.0096`、`D_CUT = 205 ms`、`D_RS_CUT = 111 ms`。它们是用 DCU 上 5 个整步点拟合出来的，**A800 上必须重拟**。
  - 拟合数据来自 §4 判决性实验的那组 fbag/fbc 点。
  - G3 判定 F50 不成立、整步对照也全部同号时，结论就是 `K_E = 0`。这同样是有效结果，照实写。
- **验证口径和 DCU 一致**：
  - 第一级：留一模型检验。指标是比原版慢的格数、相对事后最优的收益占比。
  - 第二级：样本内全对数加留一。
  - 合格线：选对率 80–90% 就算过，不要为了最后一两个点追加实验。

## 9. 已知的坑（DCU 上踩过、CUDA 上可能会复发的）

1. **栅栏只在建上下文时打一次。** 每次 op 都不能有全员栅栏或 host 同步。`barrier_all` 只在 `__init__` 和 `close` 里调用。新写代码时**不要在 op 路径上加 `torch.cuda.synchronize()` 或 `dist.barrier()`**，那会把重叠全部吃掉。
2. **`CUDA_DEVICE_MAX_CONNECTIONS=1`**：Megatron SP 要求设成 1，这时所有流共用一条硬件队列。DCU 上曾出现这样的死锁：lane 上等对端 ack 的 WaitValue 排在同一条队列里，堵住了本该释放对端的计算（`findings.md`，发射线程那一条）。生产 DX 路径在 DCU 上 `GPU_MAX_HW_QUEUES=4` 时没有死锁，但 CUDA 上的队列映射不一样。所以 G2 要在 `=1` 下跑，并且跑 ≥ 2000 个 op 的浸泡测试，确认不挂起。
3. **建上下文必须是集合调用，而且所有 rank 顺序相同。** `DXAGGemmContext` 等按 (M, K, dtype) 懒创建。vLLM 里各 rank 拿到的 M 序列相同，所以没问题；如果某个 rank 走了 stock 分支（例如 M 不在桶里），就会死锁。
4. **复用测试缓冲会产生假的"腐败"。** rig 如果复用同一块输入缓冲、DX 又原地改写了输入，就会出现复利污染。每个 op 都用新输入，见 G1 的"逐轮变异"。
5. **copy 流上的计时事件会污染结果。** 在 engine 或 lane 流上用 `enable_timing=True` 记事件，会改变整轮的输出和时序。正确性测试和性能测试只在 compute 流上记事件。
6. **跨进程比较臂时，按整次运行聚合。** 不同进程的臂之间不能按迭代逐一配对，只比较每次运行的中位数。
7. **臂之间的环境变量会泄漏。** `run.sh` 用 export 传开关，后面的臂会继承前面臂的变量。每个臂开始前必须 unset 全部 `MGD_* / OPUS_*`（DCU 上 `OPUS_AUTOTUNE / OPUS_CP` 漏过一次）。
8. **新建通信组**：所有 rank 按相同顺序调用 `new_group`，非成员也要调用。
9. **噪声检查**：容器不保证独占（`NVIDIA_VISIBLE_DEVICES=void`，没有调度器）。每一批性能测试前先把 base 连跑 3 遍。极差 > 1% 时，先查 `nvidia-smi` 有没有别的进程，再决定跑不跑。
10. **冒烟测试的数字不能引用。** DCU 上冒烟读出过 1.59×，40 次完整测试后纠正为 1.05×。
